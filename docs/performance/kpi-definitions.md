# KPI Definitions(指标口径定义)

> **Confluence 位置**:Testing & Quality → Specialized Testing → Performance Testing → 1. Strategy & Workload Model
> **状态**:Draft v0.1 · **Owner**:待指定
> **规则**:所有压测报告、CI 门禁、SLO 文档引用指标时必须使用本页口径。口径不统一,两份报告就无法对比——修改本页需评审,并注明从哪个版本的报告开始生效。

## 1. API 层指标

### 1.1 响应时间(RT)

- **测量点**:压测机发出请求第一个字节 → 收到响应最后一个字节(k6 的 `http_req_duration`)。不含 think time。
- **呈现口径**:**P50 / P95 / P99,禁止使用平均值**——均值掩盖尾部,而用户抱怨的正是尾部。最大值单独列出用于毛刺分析,不做阈值。
- **分段延迟**:端到端达不了标时,用全链路 trace 拆分到网关 / 风控 / 报盘各段(见 Monitoring & Profiling 的打点需求),分段口径为各环节入口到出口。

### 1.2 吞吐(TPS / RPS)

- **TPS**:每秒**完成且业务校验通过**的事务数。返回 200 但响应体校验失败的请求不计入有效 TPS。
- **RPS**:每秒 HTTP 请求数(含失败),仅用于描述打入负载,不作为达标结论。
- 报告必须写清打量方式:恒定到达率(`constant-arrival-rate`,按 TPS 打量)或固定 VU——两者在系统变慢时行为不同,不可混比。

### 1.3 错误率

两类错误**分开统计、并排呈现**,任一超阈值即不通过:

| 类别 | 定义 | k6 对应 |
|---|---|---|
| 传输错误 | 非 2xx/3xx、超时、连接失败 | `http_req_failed` |
| 业务错误 | 状态码正常但响应体校验失败(如下单返回 200 但无 orderId) | `checks` 失败 |

**延迟结论必须与错误率并排呈现**——快速失败的系统会"看起来更快",没有错误率的延迟数字无效。

### 1.4 容量拐点(Knee Point)

阶梯加压过程中,**延迟开始持续爬升而吞吐不再等比增长**的负载水平,即系统实际容量。报告中拐点必须附当时的饱和度证据(§3),说明卡在哪层资源。

### 1.5 WebSocket 指标

| 指标 | 口径 |
|---|---|
| 消息端到端延迟 | 服务端消息体内时间戳 → 客户端收到时刻(要求压测机与服务端 NTP 同步,误差声明在报告中) |
| 建连时间 | 发起握手 → 收到首条订阅确认 |
| 并发连接容量 | 建连成功率 ≥ 99.9% 且消息延迟达标下的最大连接数 |
| 积压 | 服务端发送队列深度;持续增长即判定推送能力不足,无论延迟数字如何 |

## 2. 前端指标(lab 口径:统一 4x CPU 节流,见 Frontend Strategy 页)

| 指标 | 口径 | 采集 |
|---|---|---|
| LCP | 页面主内容(工作台为行情/持仓主面板)完成渲染时刻 | PerformanceObserver |
| INP | 交互到下一帧绘制的延迟,取会话最差交互 | PerformanceObserver |
| CLS | 累计布局偏移分 | PerformanceObserver |
| 下单交互延迟 | **点击下单按钮 → 回报确认元素渲染完成**(自定义打点,performance.mark/measure),P95 口径;不含后端处理时的等待动画不算"完成" | Playwright 自定义打点 |
| 掉帧率 | 观测窗口内丢帧数 ÷ 应渲染帧数(60fps 基准),按行情推送速率分档报告 | CDP tracing |
| 长任务 | 主线程 >50ms 的任务计数;>200ms 单独列出 | CDP tracing |
| 内存增长 | soak 场景 JS 堆:结束值 − 稳定基线值(排除前 10 分钟预热);需 GC 后取值 | CDP `performance.memory` |
| bundle 体积 | 首屏关键路径 JS 的 gzip 后体积 | size-limit(构建期) |

## 3. 饱和度指标(服务端)

| 资源 | 关注口径 | 经验告警线* |
|---|---|---|
| CPU | 节点利用率 + run queue | 持续 >75% 视为接近饱和 |
| 内存 | RSS 趋势 + GC 频率/停顿(JVM 系) | GC 停顿进入 P99 延迟同量级即为瓶颈 |
| 连接池 | 活跃/最大比 + 等待数 | 出现等待即记录 |
| 消息队列 | 积压深度趋势 | 持续增长即不通过,与延迟无关 |
| DB | 慢查询数、锁等待 | 压测期间新增慢查询需逐条解释 |

\* 告警线为分析参考,不是通过标准;通过标准只看 SLO 页的延迟/错误率/吞吐阈值。

## 4. 测量有效性条件

不满足以下条件的数据只能作为参考,不得写入结论:

1. **预热后统计**:缓存、JIT、连接池就绪后才开始统计窗口(k6 用爬坡段排除;前端排除首次冷加载,冷/热分开报告)。
2. **单变量**:与对照数据之间只允许一个变量差异。
3. **可重复**:关键结论复跑,两次 P95 差异 >10% 视为噪声,先排查(工具容量?邻居负载?数据倾斜?)再下结论。
4. **数据规模**:铺底数据达到 Workload Modeling 假设量级,空库结果无效。
5. **环境声明**:非等比环境注明缩容比例,结论只作趋势与相对比较。

## 5. 呈现规则

- 标准结果表(所有报告统一):

  | Stage | 负载(VU 或 TPS) | RPS | P50 | P95 | P99 | 传输错误% | 业务错误% |
  |---|---|---|---|---|---|---|---|

- **分位数不可二次平均**:不同压测机 / 不同时间窗的 P95 不能取平均合并——必须由原始样本或直方图重新聚合(k6 多机结果用汇总输出,不要手工平均)。
- 趋势图纵轴从 0 开始;延迟图与错误率图并排放置。
- CI 冒烟只报"通过/失败 + 劣化项",完整分布数据入时序库供趋势查询。
