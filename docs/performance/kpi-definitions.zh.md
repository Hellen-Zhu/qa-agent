## 1. API 层通用指标

### 1.1 响应时间（RT）

- **测量点**：压测机发出请求第一个字节 → 收到响应最后一个字节（JMeter 的 `elapsed`）。**不含 think time**。
- **`elapsed` vs `Latency`**：JMeter 的 `Latency` 是首字节时间（TTFB），`elapsed` 是完整响应时间。**上传类接口（`.dat` 相关）必须同时报两者**——`elapsed - Latency` 就是服务端处理与响应传输时间，能把"上传慢"和"解析慢"区分开。
- **呈现口径**：**P50 / P90 / P95 / P99，禁止用平均值作 SLA 依据**——均值掩盖尾部，而用户抱怨的正是尾部。最大值单独列出用于毛刺分析，不设阈值。
- **分段延迟**：端到端不达标时，用全链路 trace 拆分到 API Service / UC gRPC / risk-engine gRPC / DB 各段，分段口径为各环节入口到出口。

### 1.2 吞吐（TPS / RPS）

- **TPS**：每秒**完成且业务校验通过**的事务数。返回 HTTP 200 但业务状态为拒绝的请求**不计入有效 TPS**（OREO 上尤其重要：参考数据失效时会大量出现 200 + 业务拒绝）。
- **RPS**：每秒 HTTP 请求数（含失败），仅用于描述打入负载，不作达标结论。
- 报告必须写清打量方式：**恒定到达率**（按 TPS 打量）或**固定线程数**——两者在系统变慢时行为不同，不可混比。
- ⚠️ **OREO 的 TPS 数字天然很低**（设计容量个位数，见 Workload Modeling §6）。**不要把低 TPS 读成"性能好"**——它只说明业务量小。OREO 的容量结论要看 §2 的专有指标。

### 1.3 错误率 —— 三类分离

三类错误**分开统计、并排呈现**，任一超阈值即不通过：

| 类别 | 定义 | 计入 SLA | 判定 |
|---|---|:---:|---|
| **技术错误** | HTTP 5xx、超时、连接重置、连接池耗尽 | **是** | 违反 NFR，需定位修复 |
| **业务拒绝** | HTTP 200 但业务状态为拒绝（风控未通过、参考数据失效、状态机不允许） | 否 | 单独统计"拒绝率"，**异常波动必须排查** |
| **脚本错误** | 提取器 NOT_FOUND、变量未解析、模板缺失 | 否 | **必须为 0**。非 0 则本轮结果不可信 |

**为什么必须三分**：混在一个"错误率"里的报告没法用——12% 错误率到底该找开发（技术错误）、该修数据（业务拒绝）、还是该修脚本（脚本错误）？三个结论对应三个完全不同的行动。

实现口径见 `qa/trade-performance/k6/lib/errors.js`，分类结果进 `oreo_ok` / `oreo_err_technical` / `oreo_err_business` / `oreo_err_script` 四个指标与结果 csv 的 `errClass` 标签。

### 1.4 容量拐点（Knee Point）

阶梯加压过程中，**延迟开始持续爬升而吞吐不再等比增长**的负载水平。报告中拐点必须附当时的饱和度证据（§4），说明卡在哪层资源。

> OREO 上拐点的实用价值有限（设计容量远低于拐点），仅用于了解过载行为。见 [Strategy](performance-test-strategy.zh.md) §4 中 Stress 的降级说明。

## 2. OREO 专有指标（**本页核心**）

通用模板没有这些指标，但它们才是 OREO 的容量结论来源。

### 2.1 两阶段事务计时（四眼原则）

需审批事件横跨两个业务事务，中间隔着**人工间隔**。计时口径：

| 指标 | 口径 | 说明 |
|---|---|---|
| `TX_Event_Submit` | maker 提交请求 → 收到响应（trade 已进入 pending approve） | 系统延迟，设 SLA |
| `TX_Event_Approve` | checker 点击审批 → 收到响应（事件已执行） | 系统延迟，设 SLA |
| `TX_Event_Reject` | checker 点击拒绝 → 收到响应（已从 snapshot 恢复） | **单独统计**，通常比 approve 慢 |
| `TX_Notify_Delivery` | checker_tasks 写入 → checker 端 `unread-count` 反映出该任务 | 系统延迟，设 SLA |
| **Time-to-Approve** | maker 提交 → checker 审批完成 | **业务指标，含人工间隔。不设系统 SLA** |

**硬规则：`TX_Event_Submit` 与 `TX_Event_Approve` 禁止相加或拼成一个端到端事务。** 两者之间的间隔由人决定（分钟到小时级），拼出来的数字主要反映 checker 什么时候去吃饭，不反映系统性能。

Time-to-Approve 仍需测量，但它属于**业务流程效率**指标，用于回答"checker 团队处理能力是否跟得上 maker 提交速度"（见 §2.5 队列指标），不是性能验收项。

### 2.2 扇出倍数（Fan-out Factor）

```
扇出倍数 = 单次前端 API 请求触发的下游调用次数
```

分别统计：**UC gRPC 调用数** / **risk-engine gRPC 调用数** / **DB 查询数** / **notification gRPC 调用数**。

| 判定 | 含义 |
|---|---|
| 扇出 = O(1) | 与返回行数无关，健康 |
| 扇出 = O(n)，n = 返回行数 | **N+1 问题**。blotter 返回 200 行即 200 次下游调用 |

**这是 OREO 最重要的单一指标。** 若 blotter 富化为 N+1，33 TPS 的列表查询会产生 6,600 QPS 的 UC gRPC 流量——这是唯一能让 OREO 达到三位数 QPS 的路径，也是最可能的真实瓶颈。

采集方式：APM trace span 计数，或服务端埋点计数器。**不能靠推测，必须实测**。

### 2.3 单请求成本（Cost Profile）

对 `.dat` 相关接口（`create`、`dat-to-json`、`calculate-risk-for-new`）在**1 并发**下逐档测量：

| 指标 | 口径 |
|---|---|
| 单次解析耗时 | 按文件大小档位分别报（small / medium / large） |
| **单次解析内存峰值** | 解析前 GC 后堆占用 → 解析期间最大堆占用之差 |
| **内存放大系数** | 内存峰值 ÷ 文件体积。**决定 OOM 阈值，不可假设** |
| 单次 CPU 时间 | 进程 CPU 时间增量，用于估算并发解析的 CPU 上限 |
| 耗时对文件大小的关系 | 线性 / 超线性。**超线性是设计缺陷信号** |

**理论最大并发解析数 = 可用堆 ÷ 单次内存峰值。** 这个数字若小于设计并发，就是硬容量上限，加机器之外无解。

### 2.4 单位工作量耗时（批量接口）

`bulk-approve` / `bulk-reject` / `trigger-event` / `sync-cashflows-batch` / `trade-aging` 等批量接口：

```
单位工作量耗时 = 请求总耗时 ÷ 批次内条目数
```

必须在**多个批次大小**下测量（如 1 / 5 / 20 / 50），判断：

| 形态 | 含义 |
|---|---|
| 单位耗时恒定 | 线性，健康。批量只是省了网络往返 |
| 单位耗时随批次增大而**下降** | 有批量优化（如批量 SQL），健康 |
| 单位耗时随批次增大而**上升** | **存在超线性成本**（锁范围扩大、事务过长、内存累积）。批次上限需设约束 |

报告必须同时标注**批次大小**——不标批次大小的批量接口延迟数字无法解读。

### 2.5 队列与积压指标

| 指标 | 口径 | 判定 |
|---|---|---|
| `checker_tasks` 待处理深度 | 待审批任务数随时间的曲线 | **持续单调增长即不通过**，与延迟数字无关 |
| 任务驻留时长分布 | 任务创建 → 被审批的时长 P50/P95 | 反映 checker 团队处理能力 |
| 通知投递滞后 | 任务创建 → checker 端可见 | 见 §2.1 `TX_Notify_Delivery` |

**积压是队列系统的失效模式，不是速率问题。** 一个每秒处理 100 笔但每秒到达 101 笔的系统，延迟指标可能全绿，但它正在失效。

### 2.6 事务命名与嵌套口径

事务名携带服务与模块，使 jtl 可按服务切分而无需额外埋点：

```
TX_<svc>_<module>_<api>    原子事务，与本文档 §2 及 NFR 的 PERF-xx 一一对应
TX_flow_<name>             组合事务，横跨多个原子（如 TX_flow_refdata_load）
```

在结果里按 `name` 标签前缀过滤 `workers_`，即可回答"workers 服务整体多慢"。

**两条硬口径：**

| 口径 | 说明 |
|---|---|
| **TX_flow_\* 与其内部 TX_\<svc\>_\* 不可相加** | 组合事务**包含**其内部原子事务。相加会把同一次工作计两次，TPS 直接翻倍。算吞吐时二选一 |
| **必须先按 `runPhase=main` 过滤** | setUp 前置校验 Include 的是与主链路同一份 fragment，事务名完全相同。不过滤会让 preflight 的样本混进容量统计——在 OREO 的个位数 TPS 下，多一笔就是百分之几的偏差 |

### 2.7 数据量伸缩性

同一负载在多个数据量档位下重复测量，报**劣化曲线**而非单点值：

| 数据量档位 | 用途 |
|---|---|
| 1,000 笔 | 基线（近似空库） |
| 50,000 笔 | 中期 |
| 250,000 笔 | 目标（Workload Modeling A16） |

判定：P95 随数据量的增长应为**次线性**。若 25 万笔下的 P95 是 1 千笔的 10 倍以上，说明缺索引或存在全表扫描。

**空库下的测试结果不得写入结论**（见 §5.4）。

## 3. 前端指标（lab 口径：统一 4× CPU 节流，见 Frontend Strategy 页）

| 指标 | 口径 | 采集 |
|---|---|---|
| LCP | 页面主内容（Trade Portal 为首个 blotter 表格）完成渲染时刻 | PerformanceObserver |
| INP | 交互到下一帧绘制的延迟，取会话最差交互 | PerformanceObserver |
| CLS | 累计布局偏移分 | PerformanceObserver |
| **Blotter 首次渲染** | 列表响应到达 → 表格行绘制完成，**按行数分档报告**（50 / 200 / 500 行） | 自定义打点 |
| **Blotter 刷新抖动** | 自动刷新导致的掉帧数与滚动位置是否丢失 | CDP tracing |
| **右键菜单响应延迟** | 右键点击 → 菜单可交互 | 自定义打点 |
| **生命周期事件提交交互延迟** | 点击提交 → 状态变为 pending approve 且界面反映完成（P95） | 自定义打点，`performance.mark/measure` |
| 掉帧率 | 观测窗口内丢帧数 ÷ 应渲染帧数（60fps 基准），**按 blotter 数量与刷新间隔分档** | CDP tracing |
| 长任务 | 主线程 >50ms 的任务计数；>200ms 单独列出 | CDP tracing |
| **长会话内存增长** | Soak 场景 JS 堆：结束值 − 稳定基线值（排除前 10 分钟预热）；**需 GC 后取值** | CDP `performance.memory` |
| bundle 体积 | 首屏关键路径 JS 的 gzip 后体积 | size-limit（构建期） |

> **等待动画不算"完成"。** 交互延迟的终点必须是用户能看到结果的时刻，不是请求发出的时刻。

> OREO 前端的特殊风险是**长会话 + 恒定自动刷新**：用户挂机数小时、blotter 每 30 秒重绘一次。内存增长与掉帧是主要观察项，优先级高于首屏加载。

## 4. 饱和度指标（服务端）

| 资源 | 关注口径 | 经验告警线\* |
|---|---|---|
| CPU | 节点利用率 + run queue | 持续 >75% 视为接近饱和 |
| **堆内存** | RSS 趋势 + GC 频率/停顿 | **GC 停顿进入 P99 延迟同量级即为瓶颈**。OREO 上因 `.dat` 解析尤需关注 |
| **堆内存峰值** | 单次峰值而非均值 | `.dat` 解析是脉冲式分配，均值完全掩盖风险 |
| 连接池（DB） | 活跃/最大比 + 等待数 | 出现等待即记录 |
| **gRPC 连接池 / 通道** | UC 与 risk-engine 分别统计并发流数与排队 | 扇出放大时最先耗尽 |
| **DB 锁等待** | 锁等待次数与时长，按表统计 | OREO 的 pending approve 锁争用在此体现 |
| 消息队列 | 积压深度趋势 | 持续增长即不通过，与延迟无关 |
| DB 慢查询 | 慢查询数 | 压测期间新增慢查询需**逐条解释** |

\* 告警线为分析参考，不是通过标准；通过标准只看 [OREO NFR](oreo-nfr.zh.md) 的阈值。

## 5. 测量有效性条件

不满足以下条件的数据只能作为参考，**不得写入结论**：

1. **预热后统计**：缓存、JIT、连接池就绪后才开始统计窗口（用爬坡段排除；前端排除首次冷加载，冷/热分开报告）。
2. **单变量**：与对照数据之间只允许一个变量差异。
3. **可重复**：关键结论复跑，两次 P95 差异 >10% 视为噪声，先排查（工具容量？邻居负载？数据倾斜？）再下结论。
4. **数据规模达量**：铺底数据达到 [Workload Modeling](workload-modeling.zh.md) A16 假设量级。**空库结果无效**——OREO 的 blotter 是范围查询，空库 P95 没有参考价值。
5. **参考数据已验证可用**：counterparty / portfolio 必须在 setUp 阶段真实建一笔 trade 验证过。仅"查询返回 200"不足以证明数据业务上可用（第三方停用的 counterparty 照样查得到）。preflight 失败的运行结果作废。
6. **脚本错误率为 0**：非 0 即本轮不可信，不允许扣除后达标。
7. **环境声明**：非等比环境注明缩容比例，结论只作趋势与相对比较。
8. **批量接口标注批次大小**、**上传接口标注文件大小档位**、**列表接口标注数据量与返回行数**——缺任一标注的数字无法解读。

## 6. 呈现规则

- **标准结果表**（所有报告统一）：

  | Stage | 负载 | RPS | 有效 TPS | P50 | P95 | P99 | 技术错误% | 业务拒绝% | 脚本错误% |
  |---|---|---|---|---|---|---|---|---|---|

- **OREO 专有列**按场景追加：扇出倍数 · 单位工作量耗时 · 批次大小 · 文件档位 · 数据量档位 · 内存峰值。
- **分位数不可二次平均**：不同压测机 / 不同时间窗的 P95 不能取平均合并——必须由原始样本或直方图重新聚合。
- 趋势图纵轴从 0 开始；**延迟图与错误率图必须并排放置**。
- **低 TPS 场景必须同时呈现资源占用**。OREO 的 0.1 TPS 达标毫无信息量，"0.1 TPS 时堆占用 3.2GB"才是结论。
- CI 冒烟只报"通过/失败 + 劣化项"，完整分布数据入时序库供趋势查询。
- 结果按维度切分依赖低基数标签（`runPhase` / `caseId` / `productType` 等），当前口径见 `qa/trade-performance/k6/lib/errors.js` 头注（⚠ 高基数值如 tradeId 绝不进标签）。
