## 0. 如何读这份文档

### 0.1 编号与状态

每条需求有唯一编号（如 `NFR-PERF-03`），供测试用例、缺陷、评审记录反向引用。

| 状态 | 含义 |
|---|---|
| 🟡 **提议** | 由 QA 依据业务形态提出的建议值，**尚未经签署方确认，不得作为验收依据** |
| 🟢 **已确认** | 签署方已签字，可作为验收依据 |
| 🔵 **已校准** | 上线后用真实数据修正过 |

**本文档当前全部条目为 🟡 提议状态。** 提议值不是占位符——每条都附了推导依据，签署方可以直接改数字而不必重新论证结构。

### 0.2 验证方式标签

一条需求写下来不等于它可被验证。每条需求标注**由什么活动来验证**：

| 标签 | 含义 | 谁执行 |
|---|---|---|
| **PT** | 性能测试可验证（[Test Plan](oreo-performance-test-plan.zh.md) 场景） | QA，JMeter 套件 |
| **FT** | 功能测试可验证 | QA，功能自动化 |
| **AR** | 需架构评审确认（无法通过黑盒测试证明） | 架构 |
| **OPS** | 需运维演练验证（故障注入、恢复演练） | 运维 + QA |
| **NV** | **当前不可验证**——缺少必要能力或环境 | 需先补能力，见 §12 |

标 **NV** 的条目是本文档最重要的部分：它们标出了"我们提出了要求但目前无法证明是否满足"的位置。

### 0.3 阈值来源

- 延迟与吞吐目标的**打量依据**来自 [Workload Modeling](workload-modeling.zh.md)
- 指标的**测量口径**来自 [KPI Definitions](kpi-definitions.zh.md)

## 1. 质量模型与优先级

### 1.1 OREO 的非功能优先级排序

**这个排序与多数系统不同，需要显式声明：**

```
1. 数据完整性     ← 一笔半执行的 trade 比一个慢的 blotter 严重得多
2. 可审计性       ← 四眼原则的价值全部建立在"事后可证明"之上
3. 访问控制       ← 身份可伪造则四眼原则整体失效
4. 可用性         ← 交易日内不可用直接阻塞业务
5. 性能           ← 重要，但排在上述四项之后
6. 其余
```

**依据**：OREO 是四眼原则控制的交易系统。四眼原则的产出物是**可证明的控制记录**，不是速度。一个 P95 慢 500ms 的系统会被抱怨；一个审批记录丢失或 snapshot 恢复丢字段的系统会导致监管问题与实际损失。

**这个排序有可执行后果**（见 [Strategy](performance-test-strategy.zh.md) §6.6）：任何一轮性能测试中若出现状态不一致、快照丢字段、审计缺失，**无论延迟多好都判失败**，且必须先修正确性。

## 2. 性能（NFR-PERF）

### 2.1 延迟阈值 — 读路径

计时口径见 [KPI Definitions](kpi-definitions.zh.md) §1.1；打量依据见 [Workload Modeling](workload-modeling.zh.md) §6。

| 编号 | 接口 / 事务 | P95 | P99 | 技术错误率 | 验证 | 状态 |
|---|---|---:|---:|---:|:---:|:---:|
| PERF-01 | **`GET /notifications/unread-count`** | **200 ms** | 500 ms | < 0.1% | PT | 🟡 |
| PERF-02 | **Blotter 列表 `GET /trades`**（200 行，含 UC 富化） | **1,500 ms** | 3,000 ms | < 0.1% | PT | 🟡 |
| PERF-03 | `GET /trades/{id}`（详情） | 800 ms | 1,500 ms | < 0.1% | PT | 🟡 |
| PERF-04 | `GET /trades/{id}/risk-metrics`（全量） | 2,000 ms | 4,000 ms | < 0.5% | PT | 🟡 |
| PERF-05 | RefData / UC / Product 查询 | 500 ms | 1,000 ms | < 0.1% | PT | 🟡 |
| PERF-06 | `GET /checker/tasks/pending` | 800 ms | 1,500 ms | < 0.1% | PT | 🟡 |

**PERF-01 的阈值最严，理由**：`unread-count` 是全系统请求量最大的接口（[Workload Modeling](workload-modeling.zh.md) §1，约占 33%），且不承载任何业务价值。它每慢 100ms，就在所有并发用户上乘以轮询频率地浪费连接与线程。**一个每 15 秒被 31 个用户调用的接口，没有理由超过 200ms。**

**PERF-02 是主界面阈值**，因此比详情页宽松：它要返回 200 行并做逐行富化。**但若 Fan-out Audit（[Test Plan](oreo-performance-test-plan.zh.md) S-09）证实富化为 N+1，本条阈值应下调并推动架构改造，而不是接受 1.5 秒。**

### 2.2 延迟阈值 — 写路径与计算路径

| 编号 | 接口 / 事务 | P95 | P99 | 技术错误率 | 验证 | 状态 |
|---|---|---:|---:|---:|:---:|:---:|
| PERF-07 | **`POST /trades/create`** — small 档 `.dat` | **5,000 ms** | 8,000 ms | < 0.5% | PT | 🟡 |
| PERF-08 | `POST /trades/create` — medium 档 | 10,000 ms | 15,000 ms | < 0.5% | PT | 🟡 |
| PERF-09 | `POST /trades/create` — large 档 | 20,000 ms | 30,000 ms | < 1% | PT | 🟡 |
| PERF-10 | `POST /trades/dat-to-json`（small 档） | 2,000 ms | 4,000 ms | < 0.5% | PT | 🟡 |
| PERF-11 | `POST /trades/calculate-risk-for-new` | 5,000 ms | 8,000 ms | < 1% | PT | 🟡 |
| PERF-12 | **`TX_Event_Submit`**（生命周期事件提交） | **3,000 ms** | 5,000 ms | < 0.5% | PT | 🟡 |
| PERF-13 | **`TX_Event_Approve`**（单笔审批） | **3,000 ms** | 5,000 ms | < 0.5% | PT | 🟡 |
| PERF-14 | **`TX_Event_Reject`**（单笔拒绝，含 snapshot 恢复） | **4,000 ms** | 6,000 ms | < 0.5% | PT | 🟡 |

**上传类阈值必须按文件档位分列**（PERF-07/08/09）。一个不标注文件大小的 create 延迟数字无法解读，也无法判定回归——见 [KPI Definitions](kpi-definitions.zh.md) §5.8。

**PERF-14 比 PERF-13 宽松 1 秒**，因为拒绝路径额外要做 snapshot 恢复 + 审计写入。**若实测 reject 与 approve 耗时相同，需怀疑 snapshot 恢复没有真正执行**——这是一个用性能数据反查功能正确性的例子。

**PERF-09 的 30 秒 P99 需与网关/负载均衡超时对齐**（见 RES-02）。若网关超时为 30 秒，本条实际不可能达标，用户看到的是 504 而非慢响应。

### 2.3 批量与通知路径

| 编号 | 需求 | 阈值 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| PERF-15 | `bulk-approve` 20 笔批次，**总耗时** | P95 ≤ 15,000 ms | PT | 🟡 |
| PERF-16 | `bulk-approve` **单位工作量耗时** | ≤ 750 ms/笔，且**不随批次增大而上升** | PT | 🟡 |
| PERF-17 | **`TX_Notify_Delivery`**（任务创建 → checker 端可见） | P95 ≤ 30,000 ms | PT | 🟡 |
| PERF-18 | `POST /trades/trigger-event` 单位工作量耗时 | ≤ 1,000 ms/笔受影响 trade | PT | 🟡 |

**PERF-16 的"不随批次增大而上升"比绝对值更重要。** 单位耗时上升说明锁范围或事务长度随批次膨胀（见 [KPI Definitions](kpi-definitions.zh.md) §2.4），意味着批次大小必须设上限——这是架构约束，不是调优问题。

**PERF-17 的 30 秒是按轮询间隔推导的**：`unread-count` 每 15 秒轮询一次（A12），因此 2 个轮询周期内可见是合理上限。**若前端改为 WebSocket 推送，本条阈值应大幅下调至 2 秒级。**

### 2.4 吞吐目标

| 编号 | 需求 | 阈值 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| PERF-19 | 在 [Workload Modeling](workload-modeling.zh.md) §6 全部设计容量下，PERF-01~18 同时达标 | 见 §6 目标容量表 | PT | 🟡 |
| PERF-20 | 月末场景（3× 普通日）下延迟劣化 | ≤ 20% | PT | 🟡 |
| PERF-21 | 脚本错误率 | **= 0** | PT | 🟡 |

**PERF-19 的措辞是"同时达标"而非逐个达标。** 逐个测单接口会掩盖资源竞争：`.dat` 解析与 blotter 查询在同一进程内抢 CPU，分开测都过、一起测可能都不过。

### 2.5 不作为 NFR 的项

明确排除，避免评审时反复讨论：

| 项 | 为什么不设 NFR |
|---|---|
| **Time-to-Approve**（maker 提交 → checker 审批完成） | 含人工间隔，主要由 checker 排班决定。作为**业务流程效率**指标观测（SCALE-02），不作系统 SLA |
| 容量拐点 TPS | 设计容量远低于拐点，该数字对 OREO 无决策价值（见 [Strategy](performance-test-strategy.zh.md) §4） |
| 平均响应时间 | 均值掩盖尾部，一律不作 SLA 依据 |
| 并发连接数 | 用户数以十计，非约束项 |

## 3. 可用性与连续性（NFR-AVAIL）

| 编号 | 需求 | 阈值 / 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| AVAIL-01 | 业务时段可用性（[Workload Modeling](workload-modeling.zh.md) A19：10 小时/日） | ≥ 99.9%（月度，业务时段内） | OPS | 🟡 |
| AVAIL-02 | **服务重启后，处于 `pending approve` 的 trade 不得成为孤儿** | 锁必须可恢复或可超时释放；重启后 checker 仍能审批或拒绝该笔 | **OPS + FT** | 🟡 |
| AVAIL-03 | RTO（恢复时间目标） | ≤ 30 分钟 | OPS | 🟡 |
| AVAIL-04 | RPO（数据恢复点目标） | **0**（已提交事务不得丢失） | OPS | 🟡 |
| AVAIL-05 | 计划内维护不得使 `checker_tasks` 中的任务丢失或不可见 | 维护窗口后队列完整 | OPS | 🟡 |
| AVAIL-06 | 单节点故障不影响业务连续性 | 需确认部署拓扑是否多实例 | **AR** | 🟡 |

**AVAIL-02 是 OREO 特有的高风险项。** 四眼原则会把 trade 锁在 `pending approve` 状态。若服务在锁持有期间重启：

- 锁在内存里 → 重启后锁消失，trade 状态与 `checker_tasks` 不一致
- 锁在数据库里但无超时 → trade **永久冻结**，需人工介入解锁

两种失效都不会被常规性能测试发现，必须专门做进程 kill 演练。**这条需求同时是 §4 数据完整性问题**（见 INTEG-06）。

**AVAIL-04 定为 RPO=0** 的理由：交易系统的已提交 booking 丢失不可接受。若实际架构做不到（如异步复制），必须显式降级本条并说明补偿机制。

## 4. 数据完整性（NFR-INTEG）

**本节优先级最高**（见 §1.1）。

| 编号 | 需求 | 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| INTEG-01 | **拒绝后的 snapshot 恢复必须字段完整** | reject 后 trade 应与提交前状态逐字段一致（审计与版本字段除外）。**不允许"主要字段一致"** | **FT + PT** | 🟡 |
| INTEG-02 | **事件执行原子性** | 事件要么完全生效要么完全回滚。进程在执行中被 kill 后不得留下半执行状态 | **OPS + FT** | 🟡 |
| INTEG-03 | **`pending approve` 状态的 trade 不得接受第二个事件** | 并发提交必须有且仅有一个成功，其余收到明确的业务拒绝（非 5xx、非静默覆盖） | **PT**（S-05） | 🟡 |
| INTEG-04 | `.dat` 解析失败不得留下部分创建的 trade | 解析异常、OOM、超时三种失败路径均需验证 | FT + PT | 🟡 |
| INTEG-05 | **Allocation 写放大原子性** | 一笔拆多组合时，全部子记录与父记录在同一事务内提交 | FT | 🟡 |
| INTEG-06 | 锁状态与 `checker_tasks` 必须一致 | 不存在"trade 已锁但无对应 task"或"task 存在但 trade 未锁"的状态 | **FT + OPS** | 🟡 |
| INTEG-07 | 高负载下不得出现丢更新（lost update） | 并发 amendment 必须有乐观/悲观并发控制，后写不得静默覆盖先写 | **PT**（S-05） | 🟡 |

**INTEG-01 的"不允许主要字段一致"是刻意的措辞。** snapshot 恢复的典型缺陷是漏恢复新增字段——加字段时忘了同步 snapshot 逻辑。这类缺陷在功能测试中很难发现（因为测试用例往往只断言关键字段），却会在生产中造成静默的数据错误。**建议的验证手段是全字段差异比对，而非断言列表。**

**INTEG-03 与 INTEG-07 只能通过"同目标并发"场景验证**（[Test Plan](oreo-performance-test-plan.zh.md) S-05）。常规压测每个线程打不同 trade，永远碰不到这两条。

## 5. 可审计性与合规（NFR-AUDIT）

| 编号 | 需求 | 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| AUDIT-01 | 每次状态流转都有审计记录 | 含：操作者身份、时间戳、事件类型、变更前后值、关联 trade 与 task | FT | 🟡 |
| AUDIT-02 | **高负载下审计记录不得丢失** | 一轮压测后，审计记录数必须与成功事件数**精确相等**。不允许因背压而丢弃或采样 | **PT** | 🟡 |
| AUDIT-03 | 审计日志不可篡改 | 追加写，应用层无删除/更新路径 | **AR** | 🟡 |
| AUDIT-04 | 拒绝原因必须记录且不可为空 | 背景要求"reason written to audit log" | FT | 🟡 |
| AUDIT-05 | 审计记录可按 trade / 用户 / 时间区间检索 | 用于监管问询与事后追溯 | FT | 🟡 |
| AUDIT-06 | 审计写入失败必须使业务操作失败 | **不允许"业务成功但审计失败"** | **AR + FT** | 🟡 |

**AUDIT-02 是一条性能测试可验证的完整性需求，也是本文档中最容易被忽略的一条。** 常见的性能优化手段是把审计写入改成异步 + 有界队列——队列满时丢弃。这在压测报告上表现为"延迟改善了"，实际是**用合规风险换性能**。

验证方法很简单，应纳入每轮 Load 测试的收尾步骤：

```
压测结束后：
  SELECT count(*) FROM audit_log WHERE run_id = <本轮标识>
  必须精确等于 jtl 中成功事件样本数
  差值 ≠ 0 即 AUDIT-02 失败，无论延迟指标多好
```

**AUDIT-06 与性能存在直接张力**：同步审计写入会增加延迟。这是一个必须显式做出的取舍，不能靠默认行为决定——所以它标了 **AR**，需要架构签字确认当前实现走的是哪条路。

## 6. 安全与访问控制（NFR-SEC）

| 编号 | 需求 | 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| SEC-01 | **用户身份不得由客户端自行断言** | 见下方说明 | **AR** | 🟡 |
| SEC-02 | **四眼原则不得自我满足** | 同一身份不得审批自己提交的事件，且必须由**服务端**强制，不依赖 UI 隐藏按钮 | **FT** | 🟡 |
| SEC-03 | 权限校验在服务端执行 | maker / checker 资格由服务端判定；UI 仅作展示优化 | **FT + AR** | 🟡 |
| SEC-04 | 越权访问他人 trade / task 必须被拒绝 | 直接构造请求访问无权限资源应返回 403，不得返回数据 | FT | 🟡 |
| SEC-05 | `.dat` 上传须校验类型与大小上限 | 拒绝时返回明确业务错误（见 RES-02） | FT | 🟡 |
| SEC-06 | 审计与通知中不得泄露越权信息 | 通知内容不应向无权限 checker 暴露 trade 细节 | FT | 🟡 |

### SEC-01 说明 —— 需要架构确认的一个开放问题

**现状**：所有 API 的权限由 `X-User-Id` 请求头决定。没有登录接口，没有 token，没有 401 重试路径（见 [v2 方案](../trade-api-perf-test-plan-v2-jmeter.md) §8.4）。

**为什么这在四眼系统里性质不同**：在普通 CRUD 系统里，客户端可自设身份头是一个粗糙的认证模型。在**四眼原则**系统里，它使整个控制失效——同一个人可以用 maker 身份提交、改一个请求头再用 checker 身份审批，`checker_tasks` 记录得再完整也无济于事，因为记录下来的两个身份都是攻击者自选的。

**需求措辞**：`X-User-Id` 的取值必须由客户端**无法影响**的、经过认证的组件建立（网关、mTLS、SSO 会话），且服务端必须拒绝直接来自不可信来源的该请求头。

**开放问题（需架构回答）**：

1. 是否存在网关/BFF 在认证后注入 `X-User-Id`，并剥离客户端传入的同名头？
2. API Service 是否可从公网或办公网直接访问？
3. 服务端是否校验 `X-User-Id` 与传输层身份（mTLS 证书 / SSO 会话）的一致性？

**若三问的答案是"有网关、不可直达、有校验"，则本条已满足**，应把该机制写入本条说明并改为 🟢。**这里的判断依据不足以下结论，因此标记为需架构确认，而非标记为缺陷。**

**对性能测试的影响**：压测脚本当前直接构造 `X-User-Id`（`groovy/resolve-identity.groovy`）。若引入网关认证，压测入口需相应调整——这会改变测试的接入点，属于工程影响，需提前知道。

## 7. 可伸缩性与容量（NFR-SCALE）

| 编号 | 需求 | 阈值 / 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| SCALE-01 | **Blotter 查询对数据量次线性** | 250,000 笔下的 P95 ≤ 1,000 笔下 P95 的 **3 倍** | **PT**（S-10） | 🟡 |
| SCALE-02 | **`checker_tasks` 队列不得单调增长** | 稳态下待处理深度收敛；含 checker 团队处理能力评估 | PT + OPS | 🟡 |
| SCALE-03 | 审计表与 trade 表须有归档/分区策略 | 3 年 25 万笔 trade + 数倍审计记录，需明确增长处置 | **AR** | 🟡 |
| SCALE-04 | 服务可水平扩展 | 需确认是否持有本地状态（内存锁、本地缓存、会话） | **AR** | 🟡 |
| SCALE-05 | 参考数据规模增长不影响 booking | counterparty / portfolio 由第三方同步，规模不可控 | PT | 🟡 |

**SCALE-01 的"3 倍"是提议值**，依据是：数据量增长 250 倍而 P95 只允许劣化 3 倍，等价于要求查询走索引而非全表扫描。**若实测超过 10 倍，基本可以断定缺索引或存在全表扫描**，这是本条最主要的用途——它是一个索引缺失探测器，不只是一个容量指标。

**SCALE-04 与 AVAIL-06 相关**：若服务持有内存锁（见 AVAIL-02），则它既不能水平扩展，也不能安全重启。两条需求实际指向同一个架构问题。

## 8. 可观测性（NFR-OBS）

**本节全部为"测试前置需求"**——不满足则 §2 与 §7 的部分条目无法验证。

| 编号 | 需求 | 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| OBS-01 | **暴露 gRPC 扇出计数** | 每次 API 请求触发的 UC / risk-engine 调用次数需可观测 | **NV** | 🟡 |
| OBS-02 | **暴露 `.dat` 解析内存峰值** | 单次解析的堆分配峰值需可观测（JFR / 打点） | **NV** | 🟡 |
| OBS-03 | 全链路 correlation ID | API → UC gRPC → risk-engine gRPC 可串联 | AR | 🟡 |
| OBS-04 | **服务端日志可区分三类错误** | 技术错误 / 业务拒绝 / 参数错误在日志中可区分（见 [KPI Definitions](kpi-definitions.zh.md) §1.3） | AR | 🟡 |
| OBS-05 | 暴露 `checker_tasks` 队列深度指标 | 用于验证 SCALE-02 | **NV** | 🟡 |

**OBS-01 与 OBS-02 标记 NV 的后果必须说清楚**：

- 没有 OBS-01，**Fan-out Audit 无法执行**，PERF-02 的阈值就只是一个数字，我们不知道它背后是 1 次还是 200 次 gRPC 调用。而这是 [Workload Modeling](workload-modeling.zh.md) §1 判定的首要风险。
- 没有 OBS-02，**Cost Profile 无法给出内存结论**，`.dat` 并发解析的 OOM 阈值只能靠"压到崩为止"反推——代价高、结论粗、且会污染环境。

**这两条是本文档中优先级最高的"先补能力"项**，应在正式压测排期前作为需求提给开发。

## 9. 降级与韧性（NFR-RESIL）

依赖—影响矩阵见 [v2 方案](../trade-api-perf-test-plan-v2-jmeter.md) §2.2。以下为**架构性判定标准**，无需业务确认即可生效。

| 编号 | 需求 | 阈值 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| RESIL-01 | **UC gRPC 降级期间**，`create` / `unread-count` 劣化 | ≤ 10% | PT（S-11） | 🟡 |
| RESIL-02 | **risk-engine 降级期间**，`create` / blotter 列表劣化 | ≤ 10% | PT（S-11） | 🟡 |
| RESIL-03 | **large `.dat` 高并发解析期间**，无关只读接口劣化 | ≤ 20% | PT（S-12） | 🟡 |
| RESIL-04 | **批处理运行期间**（trade-aging / sync-cashflows / refdata sync），在线接口劣化 | ≤ 20% | PT（S-13） | 🟡 |
| RESIL-05 | **notification 降级期间**，审批仍可完成 | 审批成功；任务在 pending 列表中仍可见（不依赖通知发现） | PT + FT | 🟡 |
| RESIL-06 | 下游超时须有上限且快速失败 | 不得因下游挂起而耗尽本服务连接池 | AR + PT | 🟡 |

**RESIL-02 验证的是一个架构假设，不是一个性能指标。** [v2 方案](../trade-api-perf-test-plan-v2-jmeter.md) §2.2 的结论是"create 的依赖链是 DAT parsing → DB → audit → WebSocket，不含 risk-engine，因此 risk-engine 故障时 create 在架构上应当不受影响"。**这个假设必须验证，不能默认成立**——共享线程池、共享连接池、同步的健康检查都可能让它不成立。

**RESIL-05 的措辞刻意包含"不依赖通知发现"**：若通知服务挂掉而 checker 只能通过通知得知有任务待审，则四眼流程实际中断——即使审批 API 本身完全健康。降级路径必须是"checker 主动查 pending 列表仍能看到全部任务"。

## 10. 可维护性与可配置性（NFR-MAINT）

| 编号 | 需求 | 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| MAINT-01 | **新事件类型迁入审批流应为配置变更，非代码变更** | 背景明确指出 novation / step-out / early termination 等"**暂不**"需要审批 —— 这个范围**预期会变** | **AR** | 🟡 |
| MAINT-02 | Composer 的产品定义 / lifecycle 配置变更无需部署即生效 | 配置缓存失效延迟须有上界并可观测 | FT + AR | 🟡 |
| MAINT-03 | 产品"标记删除"不得影响存量 trade 的生命周期操作 | 软删除语义需明确 | FT | 🟡 |
| MAINT-04 | 配置缓存刷新不得造成在线延迟尖刺 | 刷新期间延迟劣化 ≤ 10% | PT | 🟡 |

**MAINT-01 是本文档中唯一一条由"一个词"驱动的需求。** 业务背景描述审批范围时用的是 "does not require checker approval **yet**"。这个 "yet" 意味着当前的审批范围是一个**过渡状态**。

如果审批范围硬编码在代码里，那么每次迁移一个事件类型都需要改代码 + 回归 + 发版；如果是配置，则是一次配置变更 + 一轮验证。**这条需求的价值不在今天，在于它把一个已知的未来变更点提前标记出来**，并让架构现在就为它留出接口。

对测试的影响：[Workload Modeling](workload-modeling.zh.md) §4.3 的审批列被设计成"只改一列即可重算"，正是为了配合这条需求。

## 11. 资源上限（NFR-RES）

| 编号 | 需求 | 说明 | 验证 | 状态 |
|---|---|---|:---:|:---:|
| RES-01 | **并发 `.dat` 解析须有上限并施加背压** | 超限时排队或返回明确的业务错误，**不得 OOM**。上限值由 Cost Profile 实测的内存峰值推导 | **PT**（S-14） | 🟡 |
| RES-02 | **上传大小上限须显式拒绝** | 超限返回明确业务错误（413 或业务码），**不得表现为超时或 504** | FT | 🟡 |
| RES-03 | 网关 / LB 超时须与 PERF-09 对齐 | large 档 create 的 P99 目标 30 秒，网关超时须大于此值 | **AR** | 🟡 |
| RES-04 | DB 与 gRPC 连接池容量须覆盖设计容量下的扇出 | 含 N+1 情形下的最坏扇出（见 OBS-01） | AR + PT | 🟡 |

**RES-01 是 §2 与 §11 的交汇点。** [KPI Definitions](kpi-definitions.zh.md) §2.3 给出的公式是：

```
理论最大并发解析数 = 可用堆 ÷ 单次解析内存峰值
```

若这个数字小于设计并发（[Workload Modeling](workload-modeling.zh.md) 目标容量表：3 并发 large 档），则它是**硬容量上限**，加机器之外无解。因此 RES-01 要求的不是"调大堆"，而是**必须存在一个显式的并发闸门**——否则第 N+1 个并发解析请求会让整个 JVM 崩溃，连带杀死所有正在处理的无关请求。

**RES-03 是一个容易被漏掉的一致性检查**：如果网关超时是 30 秒而 PERF-09 的 P99 目标也是 30 秒，那么 large 档 create 在边界上会返回 504，用户看到的是错误而非慢响应。两个数字必须由架构显式对齐，且网关侧要留余量。
