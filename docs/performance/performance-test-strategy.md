## 1. 目的与范围

本页定义衍生品交易 Web 系统性能测试的整体策略：测什么、什么时候测、用什么标准判定通过。所有性能测试活动（API 压测、前端性能、CI 性能门禁）都以本页为依据。

**范围内**：交易主链路 API、行情推送（WebSocket）、高频查询接口、前端 Web 加载与运行时性能、CI 性能门禁。
**范围外**（如适用另行立项）：日终批处理性能、第三方依赖（行情源、券商/交易所网关）自身的性能。

## 2. 系统性能画像 — 为什么不能按普通 Web 系统测

| 特征 | 含义 | 对测试的要求 |
|---|---|---|
| 尾延迟敏感 | 平均延迟低但偶发毛刺，对交易用户就是事故 | 只看 P95/P99 及抖动，不看均值 |
| 脉冲型负载 | 开盘、行情剧烈波动时流量可达日常 10~30 倍，持续数秒到数分钟 | Spike 场景必须单独测，平均 TPS 达标不算过 |
| 报撤单比例高 | 量化/做市客户报撤比可达 10:1 | 负载模型必须含撤单流，不能只压"下单成交" |
| 行情 + 交易双链路 | 行情推送洪峰会抢占资源，拖累交易延迟 | 先分链路压，再做"行情满载 + 交易"合压 |
| WS 长连接 | 行情与回报走 WebSocket 长连接 | 压测工具必须原生支持 WS（k6），连接数是独立容量维度 |
| 前端长时间运行 | 用户盘中挂机数小时，行情持续刷新 DOM | 前端需要 soak 测试：内存泄漏与帧率劣化 |

## 3. 分层测试策略

| 层 | 回答的问题 | 变量 | 工具 | 详见 |
|---|---|---|---|---|
| API 层 | 服务器能扛多少并发，延迟分布如何 | 负载量 | k6 | Tooling / k6 子树 |
| 前端层 | 单个用户的浏览器里页面有多快 | 资源体积、JS 执行、渲染、设备 | Playwright + CDP | Frontend / Web Performance |
| 联动层 | 后端高负载时真实用户体验如何 | 两者叠加 | k6 打量 + 5~10 个 Playwright 会话 | Scenario Library |

三层互不替代：API 层达标不代表前端不卡，前端流畅不代表服务器扛得住。

## 4. 测试类型定义与递进关系

| 类型 | 回答的问题 | 负载形态 | 适用时机 |
|---|---|---|---|
| **Smoke** | 脚本和系统能不能跑通 | 1~5 VU，1 分钟 | 每次脚本改动、每轮压测的第一步 |
| **Load** | 预期流量下是否满足 SLO | 爬坡到目标容量，稳定 10~30 分钟 | 每次正式压测的主体 |
| **Stress** | 系统在哪里断、怎么断 | 阶梯加压超过峰值直到劣化 | 找容量拐点、验证过载行为（限流/排队/崩溃） |
| **Spike** | 能否扛住突发脉冲 | 瞬间打入数倍流量再回落 | 模拟开盘/行情突变，必测 |
| **Soak** | 长时间运行是否劣化 | 中等负载持续 2~8 小时 | 内存泄漏、连接耗尽、慢性积压 |
| **Capacity** | 目标架构最大承载多少 | 逐步扩量+扩容对照 | 上线容量规划、扩容决策 |

**递进规则（不可跳级）**：先 Smoke 验证脚本与系统 → Load 通过后 → 才做 Stress / Spike / Soak。Load 都不过，后面的结果没有意义。

## 5. 触发规则 — 什么改动必须做性能测试

| 触发条件 | 最低要求 |
|---|---|
| 每次合码（PR） | CI 性能冒烟（k6 低负载 thresholds + 前端 bundle 体积门禁），自动执行 |
| P0 交易链路代码改动 | 相关单接口基准 + 与基线对比 |
| 数据模型 / 索引 / SQL 变更 | 涉及接口的基准测试，关注生产级数据量下的表现 |
| 中间件 / 依赖版本升级（DB、MQ、网关） | 混合负载回归一轮 |
| 行情处理或推送逻辑改动 | 行情洪峰场景 + 前端行情渲染场景 |
| 前端框架升级 / 首屏路由改动 | 前端加载性能 + 关键交互延迟 |
| 发布前（每个大版本） | 完整轮次：Smoke → 基准 → 混合 → Spike → Soak，出正式报告 |

## 6. 通过 / 失败原则

1. **没有通过/失败标准的压测是演示，不是测试。** 任何场景执行前必须有书面阈值（来自 SLO & Pass/Fail Criteria 页）。
2. **标准长在脚本里**：API 层写进 k6 `thresholds`，前端写进 Playwright 断言——执行即自动判定，不依赖人看报告。
3. 比对对象二选一并在报告注明：对比 **SLO**（绝对达标）或对比 **基线**（相对劣化，如 P95 劣化 >10% 不通过）。
4. 延迟结论必须与错误率并排呈现——快速失败的系统会"看起来更快"。

## 7. 方法纪律

- **单变量**：一次只改一个变量（负载、代码版本、配置），否则结论不可归因。
- **先预热再测量**：缓存、JIT、连接池就绪后才开始统计窗口。
- **可重复**：关键结论复跑一遍，两次 P95 差异 >10% 视为噪声，先排查再下结论。
- **环境声明**：非等比环境的结果必须在报告中写明缩容比例与折算假设。
- **禁止**未经授权与协调压生产环境或第三方服务（详见 Load Testing Policy）。

## 8. 当前阶段（资产建设期）

系统尚无独立压测环境。当前所有工作以"环境到位第一天即可开跑"为目标，按模块首页 Roadmap 推进：建模与场景（纸面）、k6 脚本在功能环境 1 并发验证、造数工厂、可观测性需求前置、CI 冒烟相对基线。功能环境的测试结论**只用于趋势对比与暴露实现级问题，不外推生产容量**。
