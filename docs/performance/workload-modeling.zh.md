## 1. 最重要的结论：OREO 不是吞吐问题

先把结论放最前面，因为它决定后面所有测试怎么做。

按 §4 的 v0 假设推导（52 名具名用户、每日 120 笔 booking），OREO 的负载构成是：

| 负载来源 | 稳态 TPS | 性质 |
|---|---:|---|
| Blotter 自动刷新（31 并发 × 4 blotter ÷ 30s） | **4.13** | 恒定，与业务量无关 |
| 通知轮询 `/notifications/unread-count`（÷ 15s） | **2.07** | 恒定，与业务量无关 |
| 用户主动打开 blotter | 0.14 | 跟随用户活跃度 |
| **New booking（cutoff 小时峰值）** | **0.013** | 每 75 秒一笔 |
| Lifecycle event（cutoff 小时峰值） | 0.009 | — |

**环境负载（6.20 TPS）超过峰值业务负载（0.022 TPS）约 280 倍。**

> 口径说明：分子为 blotter 自动刷新 + 通知轮询（4.13 + 2.07）；分母为 cutoff 小时的
> booking + lifecycle event（0.0133 + 0.009）。用户主动打开 blotter（0.14）两边都不计入，
> 因为它既非定时产生、也非业务写入。§5.2 用同一口径复核。

由此得到三个不可回避的推论：

1. **OREO 全系统峰值 TPS 在个位数。** 用零售交易系统那套"打到 1200 TPS 找拐点"的方法测 OREO，会得到一份全绿但毫无信息量的报告——因为系统从来不会承受那种负载。
2. **最忙的接口是一个只返回数字的轮询接口。** `unread-count` 与 blotter 自动刷新合计约占请求总量 **97%**（其中 `unread-count` 单独占 33%），却不承载任何业务价值。**前端轮询间隔（A11 / A12）是比用户数更强的容量杠杆**——把 blotter 刷新从 30s 放宽到 60s，直接砍掉全系统约三分之一的总负载。
3. **风险不在"每秒能扛多少"，而在"单次有多贵"。** 一次大 `.dat` 解析可能吃掉数 GB 堆内存并拖停整个 JVM；一次 200 行的 blotter 查询若 UC 富化是 N+1，就是 200 次 gRPC 调用。这类问题在 1 TPS 下就会出事，**加压反而不是发现它们的手段**。

**因此 OREO 的测试重心是**（详见 [Performance Test Strategy](performance-test-strategy.zh.md) §3）：

> 单请求资源成本 · 数据量伸缩性 · 下游扇出放大 · 低并发争用 · 批处理与在线互扰 · 长时稳定性

**不是**：高 TPS 拐点 · 脉冲扛量 · 大规模并发连接。

## 2. 建模方法

没有生产数据不等于不能建模——做法是**用假设代替数据，但把每条假设显式登记**：

1. 把负载拆成**三种成分**（§3），因为它们的驱动因子和优化手段完全不同；
2. 业务假设逐条登记，标注取值、依据、确认状态（§4）；
3. 用统一公式从假设推导目标容量（§5）；
4. 产出目标容量表，作为压测打量的依据（§6）；
5. 上线后用真实数据修正假设，模型版本号 +1（§8）。

### 2.1 与零售交易系统建模的关键差异

| 维度 | 零售衍生品平台 | **OREO** |
|---|---|---|
| 用户规模 | 十万级客户 | **数十名具名用户**（maker + checker） |
| 负载驱动 | 客户数 × 委托频率 | **前端轮询间隔** + 少量高价值业务操作 |
| 峰值成因 | 开盘脉冲、行情剧变（10–30×） | **booking cutoff、月末/季末 roll、checker 批量清队列**（3–5×） |
| 单请求成本 | 均匀、轻量 | **高度不均**：`.dat` 解析与 risk 计算比查询贵几个数量级 |
| 写路径形态 | 单阶段（下单即成交） | **两阶段**（maker 提交 → 锁定 → checker 审批），见 §3.2 |
| 主要容量约束 | CPU / 网络吞吐 | **内存峰值、gRPC 扇出、DB 锁、数据量下的查询计划** |

照搬零售模型会**同时高估吞吐需求、低估单请求成本**——两个方向都错，且两个错误互相掩盖。

## 3. 负载的三种成分

### 3.1 成分拆解

| 成分 | 定义 | 驱动因子 | 与业务量的关系 |
|---|---|---|---|
| **A. 环境负载**（Ambient） | 前端定时轮询与自动刷新 | 并发用户数 ÷ 轮询间隔 | **无关**。用户挂机不操作也在产生 |
| **B. 业务负载**（Business） | booking、lifecycle event、审批 | 交易量 | 正相关，围绕 cutoff 聚集 |
| **C. 计算负载**（Compute） | `.dat` 解析、risk 计算 | booking 量 × 文件大小分布 | 正相关，但**方差极大** |

分开建模的理由：三者的**优化手段互斥**。降低 A 靠调轮询间隔（前端改一行配置）；降低 B 不可能（业务需求）；降低 C 靠算法与资源隔离。混进一个"总 TPS"里，就看不出该动哪一个。

### 3.2 两阶段写路径（四眼原则的建模后果）

OREO 对高风险生命周期事件实施四眼原则，写路径因此分裂成两种形态：

```
【需审批】新建 booking / 修改 amendment / 撤销 cancellation
  maker 提交 ──► trade 锁定为 pending approve
                 ├─ 写 checker_tasks
                 ├─ 发通知给 checker
                 └─ 存 pre-execution snapshot
                        ↓   ← 人工间隔：分钟~小时级，不是系统延迟
  checker 审批 ─┬─ approve ──► 事件执行 → trade 状态更新 → 发确认
                └─ reject  ──► 事件取消 → 从 snapshot 恢复 → 写审计日志

【暂不需审批】novation / step-in / step-out(partial|full) / early termination /
             partial novation(+remaining) / portfolio reassignment / allocation
  maker 提交 ──► 直接执行
```

**四条建模后果：**

1. **一笔需审批事件产生 2 个业务事务、约 6 次 API 调用**，中间隔着人工间隔。压测**不能**把 submit 与 approve 拼成一个连续事务计时——那个数字没有业务含义（它主要由人的午饭时间决定）。两者必须**分别计时、分别设 SLA**。
2. **reject 比 approve 贵。** approve 走正常执行路径；reject 额外要做 snapshot 恢复 + 审计写入。只测 approve 会系统性低估审批路径成本。拒绝率 A8 因此是一条必须登记的假设。
3. **pending approve 锁是争用维度。** 同一笔 trade 上的并发事件会互相阻塞。这类问题在"每个线程打不同 trade"的常规压测里**永远测不出来**，必须专门设计（见 Test Plan 场景 S-05）。
4. **`checker_tasks` 是一个会积压的队列。** 若 maker 日均提交 143 笔需审批事件而 checker 团队日处理能力不足，队列单调增长。这是容量问题但不是 TPS 问题——它的指标是**队列深度趋势**与**审批时效**，见 [NFR](oreo-nfr.zh.md) §6。

> ⚠️ 背景资料指出 novation / step-out / early termination 等**目前**（as of 2026-07）不需要审批，但用词是"暂不"（not yet）。本模型的 §4.3 必须能在这批事件迁入审批流后**只改一列**就重算，不需要重写结构。

### 3.3 Blotter：多 blotter 的请求放大

Trade Portal 页面含**多个 trade blotter**，每个 blotter 是一次独立的列表查询。因此：

```
单次页面加载的列表查询数 = 每页 blotter 数 (A10)
稳态列表查询 TPS       = 并发用户数 × 每页 blotter 数 ÷ 自动刷新间隔 (A11)
```

**A10 与 A11 的乘积效应是 OREO 最大的单一容量变量。** 4 个 blotter、30 秒刷新 → 每用户每分钟 8 次列表查询。若 blotter 列表还要走 UC gRPC 逐行富化（见 [v2 方案](../trade-api-perf-test-plan-v2-jmeter.md) §2.2 的 checker enrich 路径），扇出会再放大一个量级——这是本模型中**唯一可能达到三位数 QPS 的路径**。

### 4.7 productType —— 成本乘数，不是流量权重

**这是本模型里最容易被建错的一个维度。**

常规做法把产品类型当成混合场景里的一个流量权重（"70% 浏览 + 30% 下单"那种）。
对 OREO 不对：productType 决定的是**单请求有多贵**，而不是它出现的频率。

| productType 决定 | 影响路径 |
|---|---|
| `.dat` 结构与体积 | 解析 CPU / 内存 → `create`、`dat-to-json` |
| 观察 / 定盘次数（digital = 1，TARF / accumulator = 24+） | risk 计算复杂度 → `calculate-risk-for-new`、`risk-metrics` |
| 现金流 schedule 长度 | `generate-schedule`、`sync-cashflows-batch` |
| 可用生命周期事件集合（由 Composer 配置） | 哪些右键事件可发起 |
| 字段配置（`live-fields`） | payload 体积与校验成本 |

因此 productType 属于 **Cost Profile 的扫描维度**（Test Plan S-01），
只在全容量混合场景（S-16）里才作为配比出现——而且要取**最坏可信配比**，理由见 §4.7.3。

#### 4.7.2 按成本驱动因子分类，而不是枚举产品

产品数量随业务增长无界扩张，逐个测不可持续。做法是按**驱动成本的因子**分类，只测边界：

| 成本驱动因子 | 便宜端 | 昂贵端 |
|---|---|---|
| `.dat` 体积 / 字段数 | 单腿 vanilla | 多腿、多定盘 |
| 定盘 / 观察次数 | 1（digital） | 24+（TARF、accumulator） |
| Schedule 长度 | bullet 一次性 | 5 年月度摊还 |
| 风险模型 | 封闭解 | 路径依赖 / Monte Carlo |
| 生命周期事件面 | 少数事件 | 全套 novation / step-out |

然后选 **3 个代表产品**（A26）：最便宜、最贵、最常见。
这是功能测试里的**等价类划分 + 边界值**用在性能上——目的是**界定**成本空间，不是抽样它。

#### 4.7.3 为什么必须测退化配比，而不是平均配比

**在 120 笔/日的量级上，"平均配比"这件事根本不会发生。**

大数定律需要样本量。一个 cutoff 小时只有 48 笔（§5.2），而到达是**相关的**——
一个销售做某类产品推广，连着录 5 笔同类。这是常态，不是异常。

由此得到一条反直觉的结论：

> **高吞吐系统测平均配比；低吞吐系统必须测退化配比。**

推论：跟业务反复谈判"到底是 30% 还是 40% TARF"是低价值劳动；
测"全是最贵产品连着来"（A27）是高价值劳动。S-16 因此需要一个退化配比子场景。

#### 4.7.4 并发目标由单笔耗时推导，不由假设给定

这一节回答"要压几并发"。答案是**个位数**，且**只能在 S-01 实测出单笔耗时之后才算得出来**。

cutoff 小时的 booking 到达按泊松过程（λ = 0.0133/s，每 75 秒一笔），
在系统内的并发数服从 Poisson(λ × 单笔耗时)（M/G/∞）：

| 单笔耗时 | 提供负载 | P(≥2 并发) | P(≥3 并发) | P(≥4 并发) | **并发测试目标** |
|---:|---:|---:|---:|---:|:---:|
| 5 s | 0.067 | 0.21% | 0.005% | — | **3** |
| 10 s | 0.133 | 0.81% | 0.036% | — | **3** |
| 15 s | 0.200 | 1.75% | 0.115% | 0.006% | **4** |
| 20 s | 0.267 | 2.98% | 0.259% | 0.017% | **4** |
| 30 s | 0.400 | 6.16% | 0.793% | 0.078% | **4** |
| 45 s | 0.600 | **12.19%** | **2.31%** | 0.336% | **5** |
| 60 s | 0.800 | 19.12% | 4.74% | 0.908% | **6** |
| 90 s | 1.200 | 33.74% | 12.05% | 3.38% | **7** |

**取值规则**：取满足 `P(≥k) < 0.1%` 的最小 k。0.1% 相当于每约 1,000 笔 booking
（≈ 8 个交易日）出现一次，是"罕见但一定会发生"的合理门槛。

> **此处不再乘 A23 安全系数。** 分位数本身取的就是尾部，再乘一次是重复计算。

**两条结论：**

1. **并发目标是 2~7，不是 50。** 用几十上百线程压 create 测的不是 OREO 会遇到的情况。
2. **注意最后三行的反馈环。** 若最贵产品单笔要 45 秒，P(≥2) 从 3% 跳到 12%，
   3 并发变成每小时几次。**重叠越多 → 争用越重 → 越慢 → 重叠更多。**
   在 0.013 TPS 这种荒谬低的吞吐下，依然存在拥塞坍塌的可能——
   这也是 [NFR](oreo-nfr.zh.md) RES-01 要求"必须存在显式并发闸门"的直接依据。

#### 4.7.5 成本信封与重测触发

S-01 实测出各代表产品的成本后，把各驱动因子的上限记为**成本信封**（A28）。配套规则：

> **新产品上线时，若其成本驱动因子落在已测信封内，不需重跑性能测试；
> 超出信封（更大 `.dat`、更多定盘、更长 schedule、更重的风险模型）则必须重跑 S-01，
> 并按 §4.7.4 重算并发目标。**

这条规则让 Composer 加产品不会每次触发全量性能回归，同时又不会让一个超出信封的新产品
悄悄上线。它与 [NFR](oreo-nfr.zh.md) MAINT-01 / MAINT-02 和
[Strategy](performance-test-strategy.zh.md) §5 的触发规则配套。

#### 4.7.6 上线前从哪里拿真实的 productType 数据

**"还没上线所以没有数据"通常是错的。** 按可靠性排序：

| # | 来源 | 为什么它就是生产数据 |
|---|---|---|
| **1** | **迁移数据集 / 初始 book 导入** | OREO 要装存量组合，那批 trade 的产品分布是**真实历史成交分布** |
| **2** | **前置系统的历史成交** | 若 OREO 替代某既有系统，那个系统的 trade 表就是生产数据 |
| 3 | **Composer 产品目录** | **完整枚举**而非抽样——这一点比生产数据还强 |
| 4 | 各类型真实 `.dat` 样本 | 体积与字段数是今天就能量的结构事实 |
| 5 | 立项 / 业务案例文档 | 批准建 OREO 的材料里写了量化预期，有人签过字 |
| 6 | 交易台访谈 + term sheet 审批清单 | 哪些产品对哪些 counterparty 开放 |

**第 1、2 条优先级最高且最常被忽略**：迁移数据集把 A5（日均笔数）、A7（事件配比）、
A25（产品配比）三条假设从"猜"变成"统计"。

## 5. 推导公式与算例

### 5.1 公式

```
【A 环境负载】—— 与业务量无关
并发用户数         = (A1 + A2) × A3
通知轮询 TPS       = 并发用户数 ÷ A12
Blotter 刷新 TPS   = 并发用户数 × A10 ÷ A11
UC gRPC 扇出 QPS   = Blotter 刷新 TPS × A17          ← 仅当逐行富化为 N+1 时成立

【B 业务负载】—— 围绕 cutoff 聚集
Booking 时段均值   = A5 ÷ (A19 × 3600)
Booking 峰值       = A5 × A20 ÷ 3600
需审批事件 / 日    = §4.3 合计 = checker_tasks 到达量
审批调用 / 日      = 需审批事件 × (1 + A8)            ← approve 或 reject
批量审批突发       = A9 笔 / 次，突发形态而非速率

【C 计算负载】
并发解析数         = Booking 峰值 × 单次解析耗时       ← 耗时需实测
内存峰值需求       = 并发解析数 × A15 × A18

【设计容量】
设计容量 = 峰值 × A21 × A23      （月末场景再 × A22）
```

### 5.2 算例（全部使用 v0 示例值）

```
并发用户数         = (40 + 12) × 60%          = 31

── A 环境负载 ──
通知轮询           = 31 ÷ 15                  = 2.07 TPS   ← 恒定
Blotter 刷新       = 31 × 4 ÷ 30              = 4.13 TPS   ← 恒定
UC gRPC 扇出       = 4.13 × 200               = 826 QPS    ⚠️ 若 N+1 成立，这是真正的瓶颈
A 类合计                                      ≈ 6.2 TPS

── B 业务负载 ──
Booking 时段均值   = 120 ÷ 36,000             = 0.0033 TPS
Booking 峰值       = 120 × 40% ÷ 3600         = 0.0133 TPS = 每 75 秒一笔
需审批事件 / 日    = 120 + 15 + 8             = 143 笔
审批调用 / 日      = 143 × 1.05               ≈ 150 次
B 类合计（峰值）   = 0.0133 + 0.009           = 0.0223 TPS

── 对比（与 §1 同口径）──
A : B = 6.20 : 0.0223 ≈ 278 : 1     （计入 UC 扇出后差距进一步拉大）

── 设计容量 ──
Booking 设计容量   = 0.0133 × 4 × 2           ≈ 0.11 TPS ≈ 每 9 秒一笔
月末 booking       = 0.11 × 3                 ≈ 0.32 TPS
列表查询设计容量   = 4.13 × 4 × 2             ≈ 33 TPS
```

**读这份算例的正确方式**：不要看"33 TPS 很低所以没风险"，而要看**每一笔 booking 背后的资源成本**、以及**33 TPS 列表查询背后可能存在的 6,600 QPS gRPC 扇出**。OREO 的容量风险藏在放大倍数里，不在请求计数里。

## 7. 峰值成因（OREO 特有）

零售系统的峰值是开盘脉冲。OREO 的峰值有四个完全不同的来源，测试必须分别覆盖：

| 峰值场景 | 成因 | 形态 | 对应测试场景 |
|---|---|---|---|
| **Booking cutoff** | value date 截止前 maker 集中补录 | 1 小时内 4× 均值 | Test Plan S-02 |
| **月末 / 季末 roll** | 到期展期、估值、组合重分配集中 | 全天 3× 普通日 | Test Plan S-07 |
| **Checker 批量清队列** | checker 坐下来一次清掉 20 笔 | **突发，非速率** | Test Plan S-04 |
| **市场波动** | early termination / novation 申请激增 | 不可预测，倍数待确认 | Test Plan S-06 |

**注意 checker 批量的形态特殊性**：它不是"每秒 N 笔"，而是"一个人在 30 秒内点掉 20 笔"。用恒定到达率打量测不出它的真实行为——`bulk-approve` **单请求内含 20 笔的事务边界与锁范围**才是风险点。这也解释了 `bulk-approve` 为何被列为 P0。

## 8. 修正机制

| 时机 | 动作 |
|---|---|
| **前端确认轮询参数（A10–A12）** | **最高优先级**。这三个数决定约 97% 请求量，确认后立刻重算 §5.2 并刷新 §6 |
| **拿到迁移数据集 / 前置系统成交历史** | **优先级仅次于轮询参数**。它一次性把 A5、A7、A25 从"猜"变成"统计"，见 §4.7.6 |
| 拿到 Composer 产品目录（A24） | 确定 productType 全集，据此按 §4.7.2 选 3 个代表产品（A26） |
| S-01 实测各代表产品单笔耗时 | 按 §4.7.4 查表得出并发目标；记录成本信封（A28） |
| 新产品上线 | 检查其成本驱动因子是否超出 A28 信封；超出则重跑 S-01，见 §4.7.5 |
| 确认 `.dat` large 档体积（A15）与 blotter 行数（A17） | 重算内存峰值与 gRPC 扇出，可能改变瓶颈定位 |
| 实测解析内存放大系数（A18） | 这是唯一**不允许用假设代替**的参数：OOM 阈值不能靠猜 |
| 确认 UC 富化是否为 N+1 | 若成立，826 QPS 上升为首要容量约束，需架构评审 |
| 业务方评审 | A1–A23 逐条签字，状态改 ✅ |
| novation 等事件迁入审批流 | 只改 §4.3 的审批列并重算，结构不变（见 §3.2 注） |
| 上线后 1 个月 | 用网关日志 + RUM 替换假设值，状态改 📊，模型升 v1；目标容量表与 NFR 同步刷新 |
| 每季度 / 大版本 | 重跑 §5 推导，偏差 >20% 触发容量评审 |
