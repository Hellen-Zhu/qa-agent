# 性能观测指标体系：理论框架与本框架覆盖对照

三个业界标准框架的关系一句话：**Four Golden Signals 是总纲，RED 是它在"每个服务"上的落地子集，USE 是把第四信号（饱和度）展开到"每种资源"的落地框架**。三者不冲突，分工不同。

## 0. 基础指标与术语速查

### 0.1 缩写表

| 缩写 | 全称 | 含义 | 本框架口径 |
|---|---|---|---|
| **RPS** | Requests Per Second | 每秒 HTTP 请求数（**含失败**）——技术吞吐 | `rate(k6_http_reqs_total)`，Overview 黄线 |
| **QPS** | Queries Per Second | 每秒查询数。源自数据库领域（每秒 SQL 查询）；在 HTTP 语境常与 RPS 混用，细究时偏指**读/查询类**请求 | 本框架统一说 RPS；别人说 QPS 按语境理解（DB 层=数据库查询速率，API 层≈读路径 RPS） |
| **TPS** | Transactions Per Second | 每秒**业务事务**数——业务口径吞吐。一笔事务=1 个请求（单 API）或一串请求（journey） | 每秒业务成功笔数（`perf_ok`÷时长）；journey 语境用 journeys/hour |
| **RT** | Response Time | 响应时间：请求发出到收到完整响应 | `perf_success_duration`（只算业务成功样本） |
| **P50/P95/P99** | Percentile 分位数 | P95=95% 的请求快于此值（P50=中位数） | SLA 以 p95/p99 双线表达；见 0.2 |
| **VU** | Virtual User | 虚拟用户——k6 的并发模拟单位，closed 模型下即并发数 | Overview 绿线；ladder 的 X 轴 |
| **SLA** | Service Level Agreement | 服务水平协议——本文语境指响应时间/成功率的达标线 | `config/slas/`，判定只认成功样本 |
| **E2E** | End to End | 端到端——跨组件/跨步骤的整链视角 | 跨角色链=测量探针；journey=单角色流 |

三个"每秒"的关系一句话：**RPS 是收了多少活（技术层，含失败），TPS 是干成了多少笔业务（业务层），QPS 是 RPS 的读路径/数据库方言**。TPS ≤ RPS 恒成立，裂口=拒绝率。

### 0.2 为什么用分位数不用平均值

平均值会被两头污染：少量超慢请求把它拉高（长尾稀释），大量秒回的失败把它拉低（假快）。P95 的读法是"**95% 的用户体验不差于这个数**"——它直接管住尾部体验，这正是 SLA 的目的。P99 管更极端的尾部（100 个请求里最慢那 1 个的下限）。两条同用：p95 是常态线，p99 是尾部恶化的哨兵——p95 平稳而 p99 飙升=少数请求在排队/重试，问题刚开始。
注意分位数的两个纪律（详见 grafana 指南）：不可跨窗口聚合（5s 窗口的 p95 平均≠整轮 p95，权威在 summary 终值）；样本量不足时无意义（单发 smoke 的"p95"就是那一发的耗时）。

### 0.3 基本指标全家福（按"问什么"分组)

| 组 | 指标 | 回答的问题 |
|---|---|---|
| **量**（吞吐） | RPS、TPS、journeys/hour | 系统每秒干多少活/成多少业务 |
| **质**（时延） | RT 分位数 p50/p95/p99、max | 每件活干多快，尾部多差 |
| **稳**（正确性） | 错误率（分层：HTTP 层 vs 业务层三分类）、业务成功率 | 干的活里多少是废品 |
| **压**（施加负载） | VU/并发数、目标到达率、dropped iterations | 我们打了多少压力，施压端自己够不够（dropped>0=施压端先饱和，结论作废） |
| **饱**（服务端余量） | CPU 利用率、连接池 pending、GC、load average | 系统离"满"多远（→ §1 Saturation 与 §3 USE） |

三条铁律：**量与质必须成对读**（单看任何一个都有歧义——拐点判据=RPS 停涨 **且** p95 翘头）；**质只算成功样本**（失败秒回会虚报容量）；**先验施压再下结论**（dropped/VU 不足时测的是施压端不是系统）。

## 1. Four Golden Signals（Google SRE Book）

> 如果一个服务只能监控四个指标，就监控这四个。

| 信号 | 定义 | 关键细节 | 本框架实现 | 状态 |
|---|---|---|---|---|
| **Latency** 延迟 | 请求耗时分布 | 必须**区分成功与失败请求**的延迟——失败常秒回，混算掩盖真实水平 | `perf_success_duration`（只统计业务成功样本，SLA 判定源）；summary 双延迟（全体 vs 成功）；看板 All vs Success p95 面板 | ✅ 已覆盖，口径从严 |
| **Traffic** 流量 | 系统承受的需求量（HTTP 即 RPS） | 与容量拐点 K 对照才有意义 | `k6_http_reqs` RPS、业务 TPS（`perf_ok` 速率）、VUs 负载投递；Capacity 行三线图 | ✅ 已覆盖 |
| **Errors** 错误 | 失败率，**含隐式失败**：返回 200 但内容错误、或延迟超承诺也算错 | 隐式失败是通用工具的盲区 | 三分类引擎（technical/business/script + reason 归因）——业务失败返回 HTTP 200 也逮住；Failure Attribution 面板；verdict 判定 | ✅ 已覆盖，隐式失败是本框架核心设计 |
| **Saturation** 饱和度 | 系统离"满"还有多远（CPU/内存/池队列） | 四信号中**最有预测性**：延迟恶化是饱和的滞后表现 | 无服务端采集；施压侧仅有间接信号（open 模型 dropped_iterations、closed 模型 RPS 不再随 VU 涨） | ❌ 缺口（见 §4） |

## 2. RED（每个微服务一套）

Rate（请求速率）/ Errors（错误率）/ Duration（服务端视角延迟）。

- 本框架在**客户端视角**已有全部三项（见上表）；缺的是**服务端视角**的同名指标。
- 服务端 RED 的价值在**两侧对减**：客户端 p95 翘而服务端 Duration 平 → 问题在网络/网关；同步翘 → 问题在服务内部。这是"慢在哪一层"的第一道分叉。
- 状态：❌ 依赖现网服务端 dashboard 接入（env-checklist"服务端指标串联"项）。

## 3. USE（每种资源一套）

Utilization（利用率）/ Saturation（饱和度：队列深度、等待）/ Errors（资源层错误）。对本系统（Java 微服务）按定位价值排序：

| 优先级 | 资源指标 | 为什么 | 状态 |
|---|---|---|---|
| 1 | CPU 利用率 | 经典性能曲线缺的那条 utilization 线；拐点第一嫌疑人 | ❌ |
| 2 | JVM GC 频率与暂停 | p99 长尾与周期性毛刺的常见根因 | ❌ |
| 3 | 线程池/连接池：活跃数、**队列深度、拒绝计数** | 饱和的直接证据，比 CPU 更早报警 | ❌ |
| 4 | DB：连接池占用、慢查询、锁等待 | 写接口（create）的典型瓶颈 | ❌ |
| 5 | 下游队列：审批任务队列深度 | create 压测灌审批队列，堆积影响 checker 流（P1c） | ❌ |
| 6 | 网关：限流触发计数 | 429 的源头；与施压侧 http-429 计数对账 | ❌ |
| 7 | 基础设施：网络 RTT/重传、磁盘 I/O、容器 CPU throttling | K8s 限额节流是"CPU 不高却变慢"的隐形瓶颈 | ❌ 按需 |

另有一项施压侧自查易被忽略：**压测机自身 CPU/内存**——施压侧先饱和会把瓶颈假报到服务端（closed 模型表现为 RPS 上不去）。大并发轮次人工瞄一眼，暂不自动采集。

## 4. 缺口收敛：最小定位集

不一次接全（YAGNI）。第一批只接五个，足以把"拐点在哪一层"回答到八成：

**每服务 CPU + JVM GC + 线程池/连接池饱和度 + DB 连接池 + 网关限流计数**

接法（env-checklist 既定方案）：业务看板底部加服务端资源面板（PromQL 参照现有服务端 dashboard，按 service 过滤）；板顶加带 `?from=${__from}&to=${__to}` 的 dashboard link，把压测时间窗直接带到服务端看板，不两边手动对时间。

## 5. 汇报口径

> 平台已覆盖四大黄金信号中的三个（延迟/流量/错误），且口径比通用工具更严（成功样本延迟 + 隐式失败三分类）；第四个信号（饱和度）属服务端视角，即"服务端监控接入"事项要解决的——接入后，容量拐点的定位能力从"何时到顶"升级为"顶在哪一层"。
