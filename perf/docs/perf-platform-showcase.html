Why now

没有这个平台之前，三块最关键的面板无数可显。

交易系统的性能退化直接影响成交时效与用户操作，而问题在生产暴露的成本，远高于在压测环境提前发现。

平台的第一件事，就是让这三块面板有数。

Architecture

架构轻到极致：标准组件，零采购。

施压引擎单机即跑；指标与看板复用现网监控设施；判定权威的报告在本地产出、轮轮归档。

Ops cost

Reuse

Audit

轮轮可追溯。每轮自动归档报告、原始数据、运行日志与配置快照。

Key decisions

三个别人容易做错、我们做对的地方。

三条都来自真实教训：口径不对的性能报告，比没有报告更危险。

Verdict · 判定口径

HTTP 200 不等于成功

本系统业务失败也返回 200——通用工具会报"零错误"而实际一笔未成。平台把每个响应分为技术失败 / 业务失败 / 脚本缺陷三类，判定看业务成功率，杜绝假绿。

SLA · 统计口径

只认成功样本

失败请求往往"秒拒"，混入统计会把响应时间拉低、容量虚高。平台的 SLA 分位数只统计真实做成一笔交易的耗时。

Baseline · 回归防线

退化自动标红

达标轮通过后一键晋升为基线；此后每轮自动比对——响应时间超容差、成功率下滑、新增技术错误，第一时间标红。

Asks

需要管理层的四项支持。

平台自身零额外预算——四项全部是协调事项，不是采购事项。

01 · Accounts

压测专用账号

20 个专用账号的审批落地（应对按用户限流，方案已就绪，只差账号）。

02 · Policy

限流策略决策

容量测试是否对压测账号豁免网关限流——定口径：测"限流背后的系统容量"，还是"含限流的端到端行为"。

03 · SLA

SLA 校准会

与业务方一次会议，把各接口响应时间承诺从占位值定成正式值——判定与基线由此生效。

04 · Metrics

服务端监控接入

打通 CPU / 连接池 / GC 指标，瓶颈定位从"变慢了"升级到"慢在哪一层"。
