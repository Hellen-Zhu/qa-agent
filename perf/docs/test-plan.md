## 5. 监测指标清单（对"应该监测哪些性能指标"的答复口径）

组织框架是 Google SRE 四大黄金信号，落在两个视角上。一句话答复：**压测侧三个信号已全覆盖且口径比通用工具严，服务端现有微服务板补齐第四个（饱和度），剩三项小缺口已列入清单。**

### 5.1 四大黄金信号（Google SRE Book：如果只能监控四个指标，就监控这四个）

| 信号 | 定义 | 关键细节 |
|---|---|---|
| **Latency 延迟** | 请求耗时分布 | 必须**区分成功与失败请求**——失败常秒回，混算掩盖真实水平（本框架 SLA 只认成功样本的出处） |
| **Traffic 流量** | 系统承受的需求量（HTTP 即 RPS） | 与容量拐点对照才有意义 |
| **Errors 错误** | 失败率，**含隐式失败** | 返回 200 但内容错误也算错——三分类引擎即隐式失败的处理方案 |
| **Saturation 饱和度** | 系统离"满"多远（排队/池/队列） | **四者中最有预测性**：延迟恶化是饱和的滞后表现；排队类指标比 CPU 占用更早报警 |

### 5.2 两个视角的指标映射

**压测侧（k6，已全覆盖）**——回答"用户视角体验如何"：

| 信号 | 指标 | 口径要点 |
|---|---|---|
| 延迟 | 成功样本 p50 / p95 / p99 | 只统计业务成功请求（失败常秒回，混算掩盖真实水平） |
| 流量 | RPS、业务 TPS、VUs | 业务 TPS ≠ HTTP RPS，差值即拒绝量 |
| 错误 | 三分类（技术/业务/脚本）+ reason 归因 | 含隐式失败：HTTP 200 的业务拒绝可见 |
| 有效性 | dropped/s、样本量、空库守卫 | 结论可信度的前置门槛 |

**服务端（现有后端微服务 dashboard 已提供大部分）**——回答"系统内部余量如何、瓶颈在哪层"：

| 信号 | 指标 | 来源 |
|---|---|---|
| RED（每服务） | HTTP rate / 5xx / 延迟分位数；gRPC 进出速率与分位数 | 后端板 HTTP Traffic / gRPC 区（与压测侧两侧对减可分离网络与服务内部耗时） |
| 利用率 U | JVM 进程 CPU、Heap used vs limit、DB 连接池 active/max | 后端板 JVM & Resources / HikariCP 区；CPU + db-pending 已接入压测板 Server 面板 |
| 饱和度 S | HikariCP pending/timeout、GC 频率与暂停、线程数 | 同上——排队类指标比 CPU 更早报警，拐点定位的第一嫌疑人 |

**三项小缺口**（已在 gap/checklist 跟踪）：① 后端板错误面板只画 5xx——**限流 429 属 4xx 不可见**，需补一条序列才能与压测侧对账；② DB 主机侧（慢查询/锁等待）——应用侧连接池只见排队不见排队原因；③ OS load average 或容器 CPU throttling（若容器化部署，限额节流是"CPU 不高却变慢"的隐形瓶颈）。

### 5.3 三个易混概念：响应时间 / 吞吐 / TPS

一句话分工：**响应时间是"单笔多快"（个体视角），吞吐是"每秒收多少活"（系统技术视角），TPS 是"每秒干成多少笔业务"（系统业务视角）**。

| 概念 | 定义 | 本框架数据源 | 看板位置 |
|---|---|---|---|
| Response Time | 单请求从发出到收到完整响应的耗时，统计上用分位数表达分布 | `perf_success_duration`（成功样本口径） | Success Duration Percentiles、Overview/Capacity 行 p95 线、Run History approx 列 |
| Throughput (RPS) | 每秒处理的 HTTP 请求数，**含失败** | `rate(k6_http_reqs_total)` | Overview 黄线、Peak RPS 卡、Capacity 行 |
| TPS | 每秒**业务成功**笔数 | `perf_ok` ÷ 测试时长 | 无专门面板（分母口径歧义曾致删卡）；权威在 summary business-ok TPS；对账区 Success 卡为总量形式 |

三者的联系：

- **Little's Law**：稳态下 `并发数 = 吞吐 × 响应时间`。实测印证：closed 模型每 VU ≈ 3 req/s = 1 ÷ 0.33s——已用于 ladder 抬阶前的吞吐预测；
- **经典曲线中的镜像关系**：线性区响应时间恒定、吞吐随负载线性升；拐点后吞吐封顶、响应时间随负载恶化——**同一条容量约束，负载不足时表现在吞吐上，负载过剩时表现在响应时间上**。故拐点判据必须两条同看：RPS 增幅掉队 **且** p95 翘头；
- **TPS ≤ RPS 恒成立，裂口 = 拒绝率**：拐点附近若出现 RPS 仍涨而 TPS 掉头，即系统在以快速拒绝换吞吐——技术吞吐虚高、业务吞吐已衰退。这是"判定看业务成功率、SLA 只认成功样本"的又一依据：拐点后只有 TPS 和成功样本分位数讲真话。

记忆锚点：**RPS 是收了多少活，TPS 是干成了多少活，响应时间是每件活干多快**——三者被排队论绑定，单独任何一个都不构成结论。

完整理论对照（含 USE 框架逐资源清单与优先级）见 `metrics-theory-and-coverage.md`。
