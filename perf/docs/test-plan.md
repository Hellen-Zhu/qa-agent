# 性能测试方案（上线前五阶段计划）

制定日期：2026-08-04。定位：对上汇报与对内执行的同一份底稿——阶段表看进度，盘点表看现状，gap 表看阻塞。
执行细节不在本文重复：摸底流程见 `baseline-runbook.md`，指标体系见 `metrics-theory-and-coverage.md`，看板读法见 `grafana-metrics-guide.md`，环境就绪见 `env-checklist.md`。

场景分类法（与 `performance-test-plan.md` Purpose 对齐）。分界原则：**负载模型与测量模型分离**——一个场景的并发形态在生产中不存在，就不得用它出容量结论：

- **单 API 轮次**（负载模型，归因单元）——每轮一个端点，容量摸底、SLA 达标、回归基线（阶段 1–2）；
- **Journey · 单角色业务流**（负载模型，**真实负载单元**）——一个角色完成一次业务动作的完整调用流：主 API + 界面实际发出的伴随调用。生产并发的真实形态就是 N 个角色各自跑流，所以 journey 可以承载负载。三条 P0 journey（步骤为初稿，按 DevTools 抓包校准）：**建单 journey**（maker：查 refdata → risk-calc → datToJson → create trade）、**checker workflow journey**（checker：查待办 → approve → 查 trade 状态变更）、**lifecycle event journey**（maker：查原交易 → 触发 cancel/novation/termination → 查后续状态，P1）；
- **混合负载**（负载模型，容量与达标结论的权威）——按生产配比并发注入（阶段 3，配比被流量画像 gap #1 阻塞）。终态是**按 journey 配比混合**——生产里 create 从不独行，总带着 refdata/risk-calc 伴随调用；伴随调用契约齐前先按 API 配比过渡（现 trade-mix）；
- **E2E 跨角色链**（**测量探针，非负载模型**）——create→approve→update→approve 跨 maker/checker 紧连在生产中没有对应物（真实审批间隔是人的时延），永不高并发施压。用法：smoke 链检（零铺底全链契约回归）、单用户 baseline（整笔业务机器侧耗时）、低速探针伴随 mixed 峰值。

stress/spike/soak 叠加于负载模型之上（阶段 4）。

## 5. 监测指标清单（对"应该监测哪些性能指标"的答复口径）

组织框架是 Google SRE 四大黄金信号，落在两个视角上。一句话答复：**压测侧三个信号已全覆盖且口径比通用工具严，服务端现有微服务板补齐第四个（饱和度），剩三项小缺口已列入清单。**

### 5.1 四大黄金信号（Google SRE Book：如果只能监控四个指标，就监控这四个）

| 信号 | 定义 | 关键细节 |
|---|---|---|
| **Latency 延迟** | 请求耗时分布 | 必须**区分成功与失败请求**——失败常秒回，混算掩盖真实水平（本框架 SLA 只认成功样本的出处） |
| **Traffic 流量** | 系统承受的需求量（HTTP 即 RPS） | 与容量拐点对照才有意义 |
| **Errors 错误** | 失败率，**含隐式失败** | 返回 200 但内容错误也算错——三分类引擎即隐式失败的处理方案 |
| **Saturation 饱和度** | 系统离"满"多远（排队/池/队列） | **四者中最有预测性**：延迟恶化是饱和的滞后表现；排队类指标比 CPU 占用更早报警 |

### 5.2 两个视角的指标映射

**压测侧（k6，已全覆盖）**——回答"用户视角体验如何"：

| 信号 | 指标 | 口径要点 |
|---|---|---|
| 延迟 | 成功样本 p50 / p95 / p99 | 只统计业务成功请求（失败常秒回，混算掩盖真实水平） |
| 流量 | RPS、业务 TPS、VUs | 业务 TPS ≠ HTTP RPS，差值即拒绝量 |
| 业务事务（E2E 跨角色探针） | `perf_journey_duration`（整链机器侧耗时）、旅程成功率 | 业务口径读数、**非容量指标**：单用户 baseline 出参考值（"机器侧 X 秒，其余是人的时延"），峰值下由低速探针伴随 mixed 读取；四步全成才计时；整链耗时 − 四步单 API 基线之和 = 编排/工作流开销（唯一能测到它的口径） |
| 错误 | 三分类（技术/业务/脚本）+ reason 归因 | 含隐式失败：HTTP 200 的业务拒绝可见 |
| 有效性 | dropped/s、样本量、空库守卫 | 结论可信度的前置门槛 |

**服务端（现有后端微服务 dashboard 已提供大部分）**——回答"系统内部余量如何、瓶颈在哪层"：

| 信号 | 指标 | 来源 |
|---|---|---|
| RED（每服务） | HTTP rate / 5xx / 延迟分位数；gRPC 进出速率与分位数 | 后端板 HTTP Traffic / gRPC 区（与压测侧两侧对减可分离网络与服务内部耗时） |
| 利用率 U | JVM 进程 CPU、Heap used vs limit、DB 连接池 active/max | 后端板 JVM & Resources / HikariCP 区；CPU + db-pending 已接入压测板 Server 面板 |
| 饱和度 S | HikariCP pending/timeout、GC 频率与暂停、线程数 | 同上——排队类指标比 CPU 更早报警，拐点定位的第一嫌疑人 |

**三项小缺口**（已在 gap/checklist 跟踪）：① 后端板错误面板只画 5xx——**限流 429 属 4xx 不可见**，需补一条序列才能与压测侧对账；② DB 主机侧（慢查询/锁等待）——应用侧连接池只见排队不见排队原因；③ OS load average 或容器 CPU throttling（若容器化部署，限额节流是"CPU 不高却变慢"的隐形瓶颈）。

### 5.3 三个易混概念：响应时间 / 吞吐 / TPS

一句话分工：**响应时间是"单笔多快"（个体视角），吞吐是"每秒收多少活"（系统技术视角），TPS 是"每秒干成多少笔业务"（系统业务视角）**。

| 概念 | 定义 | 本框架数据源 | 看板位置 |
|---|---|---|---|
| Response Time | 单请求从发出到收到完整响应的耗时，统计上用分位数表达分布 | `perf_success_duration`（成功样本口径） | Success Duration Percentiles、Overview/Capacity 行 p95 线、Run History approx 列 |
| Throughput (RPS) | 每秒处理的 HTTP 请求数，**含失败** | `rate(k6_http_reqs_total)` | Overview 黄线、Peak RPS 卡、Capacity 行 |
| TPS | 每秒**业务成功**笔数 | `perf_ok` ÷ 测试时长 | 无专门面板（分母口径歧义曾致删卡）；权威在 summary business-ok TPS；对账区 Success 卡为总量形式 |

三者的联系：

- **Little's Law**：稳态下 `并发数 = 吞吐 × 响应时间`。实测印证：closed 模型每 VU ≈ 3 req/s = 1 ÷ 0.33s——已用于 ladder 抬阶前的吞吐预测；
- **经典曲线中的镜像关系**：线性区响应时间恒定、吞吐随负载线性升；拐点后吞吐封顶、响应时间随负载恶化——**同一条容量约束，负载不足时表现在吞吐上，负载过剩时表现在响应时间上**。故拐点判据必须两条同看：RPS 增幅掉队 **且** p95 翘头；
- **TPS ≤ RPS 恒成立，裂口 = 拒绝率**：拐点附近若出现 RPS 仍涨而 TPS 掉头，即系统在以快速拒绝换吞吐——技术吞吐虚高、业务吞吐已衰退。这是"判定看业务成功率、SLA 只认成功样本"的又一依据：拐点后只有 TPS 和成功样本分位数讲真话。

记忆锚点：**RPS 是收了多少活，TPS 是干成了多少活，响应时间是每件活干多快**——三者被排队论绑定，单独任何一个都不构成结论。

### 5.4 指标分层视图（沿请求路径切，每层回答一个问题）

分层原则：**上层看到的是症状，下层藏着的是原因**。信号是横轴、层是纵轴——完整监测方案是"黄金信号 × 层"的二维网格（同一套信号在不同解剖深度的投影，L1 的延迟是端到端毫秒、L5 的延迟是池 acquire time、L6 的饱和度是 load average）。

| 层 | 回答的问题 | 核心指标 | 现状 |
|---|---|---|---|
| **L1 业务/用户** | 业务受影响了吗？ | 业务 TPS、业务成功率、端到端响应时间（成功样本分位数） | ✅ k6 三分类 + summary + 看板 |
| **L2 接入/网关** | 问题在入口策略还是后端？ | 网关 RPS、4xx/429 限流计数、转发延迟 | 🟡 429 不可见（后端板 5xx-only，已记 checklist） |
| **L3 服务**（每微服务） | 哪个服务慢？ | RED：请求率/错误率/延迟分位数；gRPC 进出与放大系数 | ✅ 后端板 HTTP Traffic + gRPC 区 |
| **L4 运行时**（进程内） | 这个服务为什么慢？ | 进程 CPU、Heap、GC 频率/暂停、线程池活跃/队列 | ✅ 后端板 JVM 区；CPU 已接入压测板 |
| **L5 依赖/数据** | 是不是在等别人？ | DB 池 active/pending/timeout、慢查询/锁等待、MQ 队列深度、下游延迟 | 🟡 池指标有（pending 已接入）；DB 主机侧与审批队列缺 |
| **L6 基础设施** | 物理资源到顶了吗？ | 主机 CPU/load average、内存、磁盘 I/O、网络 RTT、容器 throttling | ⚪ 未接，按需 |

三条使用纪律：

1. **自顶向下钻取，不反向**——从 L1 症状出发逐层下问，某层答"是"即根因层；底层资源异常若 L1 无感，不构成问题；
2. **层间对减是定位核心手法**——相邻层同名指标相减即中间环节耗时：k6 响应时间 − 服务端 duration = 网络+网关；服务 duration − DB usage time = 服务自身计算。每一层边界都可做一次对减；
3. **分层把模糊陈述变成有限排查路径**——现案：L1 说响应 330ms（症状）、L4 说 CPU 近零（不是我）→ 嫌疑自动收敛到 L5（等待）与 L2（转发），下一步动作即对减定位。

完整理论对照（含 USE 框架逐资源清单与优先级）见 `metrics-theory-and-coverage.md`。

## 6. 测试数据策略（Test Data Approach）

性能数据分三类，机制与纪律各不相同：

| 类别 | 定义 | 框架机制 | 例子 |
|---|---|---|---|
| **参数池**（可复用） | 请求参数的取值集合，重复使用不改变系统状态 | 用例行数据模型 + 全局游标轮转（`pickAt`/`pickTradeId`） | 查询过滤条件、detail 的 ID 池、update 的 payload 行 |
| **消耗池**（一次性） | 每笔请求消耗一个、用后即"脏"的前置数据 | seed 流水线产出 + exactly-once 游标 + 量级 preflight（池 ≥ 计划迭代 ×1.2） | update 的 LIVE tradeId、approve 的 pending taskId |
| **存量水位**（环境属性） | DB 既有数据规模，影响查询/索引性能 | 水位带维持 + 每轮 manifest 记录 + 与基线失效纪律联动 | trade 表总行数 |

两条场景级推论：**E2E 旅程零消耗池**——create 自产 update 所需的 LIVE trade、TaskId 从响应 msg 收割，是唯一自给自足的写场景（代价：一条旅程烧 maker+checker 双份限流预算）；**mixed 一轮双池并耗**——update-ids 与 approve-tasks 同时消耗（单池需求 = 单流速率 × 时长 × 1.2，preflight 强制），跑前双 seed、跑后双脏。

**铺底路线**（按真实性排序，当前默认第一条）：

1. **API 铺底**（默认）：create→approve 走全业务逻辑，关联表/审计/状态机天然正确——真实性无价；
2. **数据工厂**（条件启用，gap #8）：开发维护的 DB 直插脚本，铺底耗时成瓶颈时启用；**等价性验证准入**：直插样本与 API 样本各跑一轮，响应时间分布一致才可用——直插漏关联数据会让服务端走异常分支，性能数据隐蔽失真；
3. **快照恢复**（独占环境理想态）：一致性、清理、可重复三合一，依赖环境独占与平台配合。

**一致性纪律**：追求的不是"每轮环境字节级相同"，而是**影响性能的因子在同一水位带**——存量行数、索引统计、缓存冷热（warm-up 已覆盖）。跨轮对比先对水位，水位差超带宽不做同口径对比。

**清理纪律**：清理键 = 专用 PERF portfolio + 状态 + 时间窗（建档时即预埋）；主力是环境方的级联清理脚本（gap #9），业务 API（cancel/reject）不作清理主力——慢且多为软删除、水位不降。

**复用纪律**：铺底产物不浪费——测量轮结束后，seed 出的 trade 即 detail/risk-metrics 场景的真实 ID 池（读接口允许使用真实存量数据）。
