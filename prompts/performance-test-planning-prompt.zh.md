# 性能测试方案规划 · 提示词（中文版）

> 用途：当 AI 能访问前后端代码时，用这份提示词让它规划一套性能测试方案。
>
> 核心原则：**能从代码里挖出来的，不要手喂；代码里挖不到的（业务量、SLA、环境），你必须主动提供。** 提示词的主要工作是"派活 + 给约束 + 定产出"，而不是描述系统。

---

## 提示词正文

```
# 角色
你是一名资深性能测试工程师。你可以访问本项目的前后端完整代码。

# 目标
为本系统制定一份性能测试方案。测试目的是：【上线验收 / 容量评估 / 建立性能基线，三选一或组合】。

# 第一步：请先分析代码，提取以下事实（不要臆测，基于代码给出，并标注文件位置）
1. 对外接口清单，以及每个接口背后的调用链路（Controller → Service → DAO/外部调用）。
2. 识别"重操作"：涉及大数据量查询、批量处理、导出、复杂聚合、循环调用的接口。
3. 数据库访问：关键 SQL、是否有分页、涉及的表、可能缺索引或存在深分页/全表扫描的查询。
4. 外部与中间件依赖：第三方 API、缓存(Redis)、消息队列、定时任务——列出并标注哪些在压测中会产生真实副作用（发短信/扣款/写下游）。
5. 异步落库点：哪些操作是"接口返回成功但实际异步写库"，需要特殊验证。
6. 资源配置：Web 容器线程池、数据库连接池、HTTP 客户端连接池的当前配置值。
7. 前端：识别首屏加载重、请求瀑布长、或一次性拉取大量数据的页面。

# 第二步：结合以下业务约束（代码里读不到，我提供）
- 用户规模：总用户 __，日活 __，高峰时段 __
- 峰值模式：是否有"齐步走"场景（如全员打卡、月末集中操作）__
- 数据量：核心表现有数据量 __，年增长 __，需按 2~3 年后的量级铺底
- SLA/验收标准：P95 响应时间 ≤ __ 秒，错误率 < __%，目标并发 __
- 测试环境：配置相对生产为 __（等比 / 缩水多少），可用工具 __

# 第三步：产出性能测试方案，包含
1. 测试场景设计（单接口基线 + 混合业务场景，含各操作比例、并发梯度）
2. 每个场景的验收指标（对齐上面的 SLA）
3. 重点监控指标与布点（基于你在第一步识别的瓶颈预判）
4. 铺底数据与参数化数据方案
5. 外部依赖的处理建议（真实调用 / mock / 挡板），并说明理由
6. 风险与规避（压测副作用、数据污染、共用中间件影响）
7. 建议的执行顺序与迭代轮次

# 约束
- 本轮只做"方案规划"，不要写压测脚本。
- 把"代码中确认的事实"与"你的推断/假设"明确分开标注。
- 最后单独列出：为完成方案，你还需要我确认哪些信息（缺口清单）。
```

---

## 使用要点

1. **把"第一步"当成 AI 的核心价值区。** 它从代码里提取的"重操作清单""缺索引的 SQL""会产生真实副作用的依赖"，正是人工梳理最费时、最易漏的部分。场景设计、监控布点、风险预案都从这里长出来。

2. **"第二步"是你不可替代的输入。** 用户量、峰值模式、SLA、环境等比性——代码里没有，AI 只能猜。把和领导谈下来的数字填进去，方案质量直接取决于此。

3. **强制区分"事实 vs 假设"并输出缺口清单**——这是防止 AI 幻觉的关键。你的复核工作量会从"通读全文找错"降到"只查它标记为假设的几条"。

## 推荐的迭代用法（分两轮）

- **第一轮**只发"第一步"，让它先出一份**代码分析报告**（接口清单、重操作、依赖、瓶颈预判）。你核对无误、补充遗漏。
- **第二轮**再带着确认过的分析结果 + 业务约束，让它出完整方案。

这样把"AI 读代码"和"AI 做规划"解耦，每一步都可校验，比一把梭更可靠。
